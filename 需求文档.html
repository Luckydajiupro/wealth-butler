1. 项目概述

1.1 项目背景与目标

XX科技有限公司计划建设一套"智能财富管家系统"，服务于公司内部员工（理财顾问、风控专员、客户经理）和外部客户（零售投资者、高净值客户）。

当前业务流程痛点：

痛点现状期望
客户服务依赖人工客服逐一解答，等待时间长，服务标准不统一AI 7×24小时响应，话术统一
投顾推荐理财顾问凭经验手动研判客户画像、逐页翻阅产品手册AI 自动生成客户画像、智能筛选匹配产品
风控预警风控专员每日人工抽查交易流水，遗漏率高AI 实时逐笔匹配规则，分级预警
数据查询内部员工提工单给IT部门，由IT编写SQL导出员工用自然语言提问，AI自动生成SQL并返回结果
业务操作多个系统切换，操作繁琐自然语言一句话完成申购、赎回、转账等操作

系统需要实现：

  • 客户可自然语言咨询金融产品、查询持仓、办理业务
  • 理财顾问可获取AI辅助的客户画像分析和产品推荐
  • 风控专员可通过AI实时监测异常交易并获得分级预警
  • 内部员工可通过自然语言查询业务数据、执行标准业务操作

核心目标：用AI Agent技术替代传统客服+人工研判流程，提升服务效率，降低人力成本，同时确保合规性和风控能力。

2.3 核心技术组件说明

2.3.1 RAG（检索增强生成）

数据流：

flowchart LR A[用户提问] --> B[Query Embedding] B --> C[(Milvus<br/>相似度检索)] C --> D[TopK文档片段<br/>+ Score] D --> E[Prompt 组装<br/>Query + 文档片段] E --> F[LLM 生成<br/>回答 + 引用]

工作原理： 1. 离线索引：将知识库文档（FAQ、产品说明、政策法规）解析→分块（512 token，overlap 64）→ Embedding生成→存入Milvus 2. 在线检索：用户提问→问题Embedding→Milvus TopK检索→返回最相似的K个文档片段（带相似度分数） 3. 增强生成：将检索到的文档片段拼接到System Prompt→连同用户问题一起送入LLM→生成带来源引用的回答 4. 兜底策略：若最高Score低于阈值，返回"抱歉，暂时无法回答该问题，建议联系人工客服"

2.3.2 GraphRAG（图谱增强检索）

数据流：

flowchart TD A[用户提问] --> B[实体识别<br/>产品名/风险等级/行业/客户名] B --> C[(Neo4j<br/>多跳图谱查询)] C --> D[关联实体列表<br/>+ 关系路径] A --> E[RAG 向量检索<br/>TopK 文档片段] D --> F[融合排序<br/>向量Score×α + 图谱Score×β] E --> F F --> G[LLM 增强生成]

工作原理： 1. 实体识别：从用户问题中提取关键实体（产品名、风险等级、行业、客户名等） 2. 图谱查询：提取的实体→Neo4j Cypher多跳查询→获取关联实体和关系路径 3. 融合排序：将向量检索结果和图谱查询结果按综合分数排序，注入LLM上下文 4. 增强生成：LLM同时获得文本语义信息和图谱结构信息，生成更准确的回答

2.3.3 NL2SQL（自然语言转SQL）

数据流：

flowchart TD A["用户提问（自然语言）"] --> B["Schema 注入<br/>System Prompt + DDL + 注释"] B --> C["Few-shot 示例<br/>3-5 个典型案例"] C --> D["LLM 生成 SQL<br/>仅允许 SELECT"] D --> E["安全校验<br/>禁止 DROP/DELETE/UPDATE/INSERT"] E --> F["MySQL 执行 SQL"] F --> G["查询结果集"] G --> H["LLM 结果解读<br/>自然语言描述"]

工作原理： 1. Schema注入：将所有相关表的CREATE TABLE语句（含字段注释）作为System Prompt注入LLM。为避免 Prompt 过长，采用动态 Schema 筛选：根据用户问题中的关键词（如"持仓"→注入 fin_holdings+fin_product，"客户"→注入 sys_user+fin_customer_profile），只注入相关表的 DDL，而非全部 10 张表 2. Few-shot示例：提供3-5个"自然语言→SQL"的典型示例，提升生成准确率 3. SQL生成：LLM根据用户问题和Schema生成SELECT语句 4. 安全校验：正则检查SQL中是否包含DROP/DELETE/UPDATE/INSERT等危险操作，若包含则拒绝执行 5. 执行与解读：安全SQL送入MySQL执行→结果集+原始问题→LLM生成自然语言解读

2.3.4 NL2API（自然语言转API调用）

数据流：

flowchart TD A["用户指令（自然语言）"] --> B["意图识别（LLM 分类）<br/>8 种业务意图"] B --> C["参数提取<br/>Function Calling"] C --> D["权限校验（RBAC）<br/>角色 + 操作权限矩阵"] D --> E["二次确认<br/>申购>1万 / 转账>5万"] E --> F["API 执行<br/>调用 FastAPI 业务接口"] F --> G["操作结果<br/>成功/失败 + 详情"]

工作原理： 1. 意图识别：LLM将用户自然语言分类为8种业务意图之一 2. 参数提取：利用Function Calling从自然语言中提取结构化参数 3. 权限校验：根据操作人角色（RBAC）检查是否有权执行该操作 4. 二次确认：高风险操作需用户二次确认（"确认为客户张三申购10万元XX稳健增利债券A？"） 5. API执行：调用对应的FastAPI业务接口完成操作

3. 数据库设计

3.1 MySQL核心表结构

以下为引用sql设计草稿.txt中的10张核心表，逐表补充业务说明。

表1：sys_user — 统一用户表

业务用途：客户与员工共用一套账号体系，通过user_type字段区分。员工角色（理财顾问/风控专员/客户经理/管理员）和客户等级（普通/金卡/白金/钻石/私行）通过字段隔离，避免冗余建表。

核心字段业务含义：

字段类型业务含义
idBIGINT全局唯一用户标识，作为所有关联表的外键
usernameVARCHAR(64)登录账号，唯一约束
password_hashVARCHAR(255)BCrypt/Argon2加密后的密码，不存明文
user_typeVARCHAR(16)CUSTOMER=客户，EMPLOYEE=员工
employee_roleVARCHAR(32)仅员工有效：理财顾问/风控专员/客户经理/管理员
customer_levelVARCHAR(16)仅客户有效：普通/金卡/白金/钻石/私行
statusVARCHAR(16)账号状态：正常/禁用/冻结

关键查询场景：

  • 按user_type筛选客户列表或员工列表

查询示例（Cypher语句）

多跳产品推荐：

cypher
// 为客户A（risk_level=C2稳健型）推荐匹配产品，按预期收益率降序
MATCH (p:Product)-[:SUITABLE_FOR]->(rl:RiskLevel)
WHERE rl.level_code IN ['C1', 'C2']
  AND p.status = '在售'
RETURN p.product_name, p.product_type, p.expected_return, p.risk_level
ORDER BY p.expected_return DESC
LIMIT 10

客户持仓穿透查询：

cypher
// 查询客户张三的所有持仓，穿透到行业和市场
MATCH (c:Customer {name: '张三'})-[h:INVESTS_IN]->(p:Product)-[:BELONGS_TO]->(i:Industry)-[:LOCATED_IN]->(m:Market)
RETURN c.name AS 客户, p.product_name AS 产品, h.shares AS 份额,
       h.current_value AS 市值, i.industry_name AS 行业, m.market_name AS 市场

行业集中度分析：

cypher
// 统计某客户的持仓行业分布，检测集中度风险
MATCH (c:Customer {name: '张三'})-[:INVESTS_IN]->(p:Product)-[:BELONGS_TO]->(i:Industry)
WITH c, i, SUM(p.expected_return) AS total_return
WITH c, COLLECT({industry: i.industry_name, weight: total_return}) AS industries
RETURN c.name AS 客户, industries AS 行业分布

F1.2 RAG知识库搭建

  • 文档解析模块：
    • 支持格式：txt、md、docx
    • 分块策略：512 token / 块，overlap 64 token
    • 保留标题层级信息作为metadata
  • Embedding生成与Milvus入库：
    • 调用Embedding API生成向量
    • 按知识类型存入对应集合（FAQ / 产品 / 政策）
  • 元数据同步（fin_knowledge_meta表）：
    • 每次上传文档后，先在 fin_knowledge_meta 中创建一条元数据记录
    • 记录包含：knowledge_type、title、source_file、minio_path、milvus_collection、version（默认v1）、status（默认"有效"）、expire_at（政策法规类默认1年，产品说明默认半年）
    • Milvus 向量记录的 metadata.source_id 关联此元数据记录的 id
    • 删除文档时：同步标记 fin_knowledge_meta.status 为"过期"，删除 Milvus 向量，MinIO 文件标记归档
  • 知识库检索接口：
    • POST /api/knowledge/search
    • 输入：query文本，TopK数量（默认5）
    • 输出：TopK文档片段 + 相似度Score + 来源信息
  • 知识库管理接口：
    • POST /api/knowledge/upload — 上传文档并自动入库
    • GET /api/knowledge/list — 查看文档列表
    • DELETE /api/knowledge/{id} — 删除文档及对应向量
  • 导入已有FAQ问答对（问答对文本版.txt，40组）作为初始知识库

F1.3 智能客服Agent

  • 对话接口：POST /api/chat/customer
    • 请求体：{ session_id, message, user_id }
    • 响应体：{ reply, sources: [...], session_id }
    • 支持多轮对话（通过session_id关联上下文）
  • 意图识别：
    • 产品咨询 → RAG检索产品知识库
    • 政策解读 → RAG检索政策知识库
    • FAQ → RAG检索FAQ知识库
    • 闲聊 → LLM直接回复（友好引导到业务话题）
    • 转人工 → 返回"正在为您转接人工客服..."
  • RAG检索+LLM生成回答：
    • System Prompt包含检索到的文档片段
    • 回答末尾附带来源引用：【来源：《XX产品手册》第3章】
  • 短期记忆：
    • 基于Redis的会话上下文管理
    • Key：session:{session_id}:messages
    • Token预算控制（最多保留最近N轮对话，总Token不超过4096）
    • 30分钟过期，最长24小时
  • 兜底策略：
    • 检索最高Score < 0.7 → "抱歉，我暂时无法回答这个问题。建议您拨打客服热线400-XXX-XXXX咨询人工客服。"

功能需求

F2.1 客户画像系统

  • 画像录入接口：POST /api/profile/create
    • 从对话中提取客户标签（风险偏好、资产规模、投资经验等）
    • LLM信息抽取：输入对话文本 → 输出结构化标签JSON
    • 写入fin_customer_profile表 + Redis缓存
  • 画像查询接口：GET /api/profile/{customer_id}
    • 先查Redis缓存，未命中则查MySQL并回填缓存（Cache-Aside）
    • 返回完整画像信息（风险等级、投资偏好、资产规模、置信度等）
  • 画像更新接口：PUT /api/profile/{customer_id}
    • 增量更新标签
    • 新标签与旧标签冲突时的处理策略：
    • 来源置信度高的覆盖低的（如AI评估 > 用户自述）
    • 相同来源则新数据覆盖旧数据
    • 保留冲突记录用于审计
  • 画像研判引擎：基于"投资者风险画像研判规则.md"实现四维度加权打分
    • 基础属性特征（25%）：年龄、学历、职业、收入
    • 投资经验特征（25%）：投资年限、产品类型、交易频率
    • 风险偏好特征（30%）：风评得分、亏损承受度
    • 行为异常特征（20%）：交易频率异常、集中度风险
    • 加权总分 → 映射到C1-C5风险等级
  • 硬性门槛熔断：
    • 年龄 < 18 或 > 80 → 需特批（标记为"需人工审核"）
    • 无收入 且 资产 < 1万 → 仅允许R1-R2产品
    • 风评过期（valid_until < 当前日期）→ 冻结画像权限，提示重新评估
  • 画像置信度：
    • 每个标签携带置信度分值（0.00-1.00）
    • 来源决定初始值：风评问卷=0.9、AI对话提取=0.6、用户自述=0.4、默认值=0.2

F2.2 风险评估模块

  • 风评问卷接口：GET /api/risk/questionnaire
    • 返回16道评估题目（题目内容需Mock，覆盖收入、投资经验、风险承受力、投资目标等维度）
    • 每题4个选项（A/B/C/D），各选项对应不同分值
  • 风评提交接口：POST /api/risk/assessment
    • 请求体：{ customer_id, answers: [{q:1, a:"B"}, ...] }
    • 计算总分 → 判定风险等级(C1-C5)：
    • C1保守型：0-20分
    • C2稳健型：21-40分
    • C3平衡型：41-60分
    • C4进取型：61-80分
    • C5激进型：81-100分
    • 写入fin_risk_assessment表
    • 更新fin_customer_profile的risk_level和risk_score
  • 适当性匹配检查：POST /api/risk/suitability-check
    • 输入：customer_id + product_id
    • 客户风险等级（C1-C5）vs 产品风险等级（R1-R5）匹配规则：
    • C1 → 仅R1
    • C2 → R1-R2
    • C3 → R1-R3
    • C4 → R1-R4
    • C5 → R1-R5
    • 不匹配时返回警告并记录日志

F2.3 数据分析Agent（NL2SQL）

  • 自然语言查询接口：POST /api/chat/analyst
    • 请求体：{ session_id, message, user_id }
    • 响应体：{ reply, sql, query_result, session_id }
  • SQL生成模块：
    • 将10张表的CREATE TABLE语句（含COMMENT）作为System Prompt注入LLM
    • 提供3-5个few-shot示例（自然语言→SQL对照）
    • LLM生成SELECT语句
  • 安全校验：
    • 正则检查：禁止DROP/DELETE/UPDATE/INSERT/ALTER/TRUNCATE等危险操作
    • 仅允许SELECT查询
    • 查询结果行数限制（最多100行）
  • SQL执行与结果格式化：
    • 执行安全SQL → 返回结果集
    • 结果格式化为表格/列表形式
  • 结果解读：
    • 查询结果 + 原始问题 → LLM生成自然语言描述
    • 如："上季度理财产品总收益率为4.32%，较去年同期上升0.5个百分点"
  • 支持场景：
    • 持仓查询："客户张三目前持有哪些产品？"
    • 收益统计："上季度各产品类型的平均收益率是多少？"
    • 交易记录："客户A最近一个月的交易记录"
    • 客户统计："AUM超过100万的客户有多少个？"

功能需求

F3.1 Neo4j知识图谱构建

  • 图谱数据模型设计（节点+关系）：
    • 节点：Customer、Product、RiskLevel、Industry、FundManager
    • 关系：HAS_RISK_LEVEL、INVESTS_IN、BELONGS_TO、MANAGED_BY、SUITABLE_FOR
  • 数据导入脚本：
    • 从MySQL导入产品数据 → (:Product) 节点
    • 从MySQL导入客户持仓数据 → (:Customer)-[:INVESTS_IN]->(:Product) 关系
    • 从MySQL导入风评数据 → (:Customer)-[:HAS_RISK_LEVEL]->(:RiskLevel) 关系
    • Mock行业/市场/基金经理数据 → (:Industry)、(:Market)、(:FundManager) 节点
    • 产品→行业关联 → (:Product)-[:BELONGS_TO]->(:Industry) 关系
  • 图谱管理接口：
    • GET /api/graph/stats — 查看节点统计、关系统计
    • GET /api/graph/visualization/{customer_id} — 返回图谱可视化数据（节点+边的JSON）
  • Cypher查询封装为Tool：
    • get_customer_products(customer_name) — 查询客户持仓产品
    • get_product_industry(product_name) — 查询产品所属行业
    • get_suitable_products(risk_level) — 查询适当性匹配产品
    • get_industry_distribution(customer_name) — 客户持仓行业分布

F3.2 GraphRAG增强检索

  • 在RAG基础上增加图谱查询路径
  • 实体识别：
    • 从用户问题中提取实体（产品名、风险等级、行业、客户名等）
    • 可用LLM NER或正则匹配
  • 图谱关联查询：
    • 提取的实体 → Neo4j多跳查询 → 补充上下文
    • 如："张三持有的产品属于哪些行业？" → 提取"张三" → 图谱查询客户→持仓→产品→行业
  • 融合排序：
    • 向量检索结果（Score_A）+ 图谱查询结果（Score_B）
    • 综合Score = α × Score_A + β × Score_B（α=0.6, β=0.4 可配置）
    • 去重后按综合Score降序注入LLM

F3.3 投顾助手Agent

  • 对话接口：POST /api/chat/advisor
    • 请求体：{ session_id, message, user_id, customer_id }
    • 响应体：{ reply, recommendations: [...], reasoning, session_id }
  • 客户画像读取（从Redis/MySQL获取中期记忆）
  • 产品推荐流程：

1. 读取客户画像（风险等级、偏好、资产规模） 2. 适当性过滤（只保留风险匹配的产品：C1→R1，C2→R1-R2，以此类推） 3. 图谱增强（利用Neo4j做产品-行业-市场关联分析，避免行业过度集中） 4. 综合排序（收益率、风险、期限匹配度加权打分） 5. 生成推荐理由（引用客户画像信息，如"鉴于您稳健型的风险偏好..."）

  • 资产配置建议：
    • 根据客户画像生成配置比例建议
    • 如：保守型 → 货币30% + 债券50% + 股票10% + 现金10%

F3.4 业务操作Agent（NL2API）

  • 对话接口：POST /api/chat/operator
    • 请求体：{ session_id, message, user_id }
    • 响应体：{ reply, action, params, status, session_id }
  • 意图识别：区分8种业务操作：

1. 产品申购 — "帮客户A申购10万元XX产品" 2. 产品赎回 — "赎回客户B持有的XX产品全部份额" 3. 转账 — "把客户A的50万转到客户B账户" 4. 风评重做 — "给客户A重新做风险评估" 5. 信息更新 — "把客户A的手机号改成138XXXXXXXX" 6. 产品查询 — "查一下XX产品的最新净值"（注：仅限员工/顾问查询产品详细数据，不同于客服 Agent 的产品咨询——后者面向客户进行产品推荐和一般性咨询，不涉及具体净值、份额等业务数据） 7. 可疑上报 — "上报客户A的可疑交易" 8. 工单创建 — "为客户A创建一个投诉工单"

  • 参数提取：
    • 从自然语言中提取操作参数（产品名、金额、客户ID、手机号等）
    • 使用Function Calling / Tool Use模式
  • 权限校验：
    • 检查操作人角色是否有权限执行该操作
    • 理财顾问：可执行申购/赎回/风评/产品查询
    • 客户经理：可执行信息更新/工单创建
    • 风控专员：可执行可疑上报
  • 二次确认：
    • 高风险操作需用户确认：
    • 申购金额 > 1万元
    • 转账金额 > 5万元
    • 确认流程："确认为客户张三申购10万元XX稳健增利债券A？请回复'确认'执行"
  • API执行：调用对应业务接口
  • 结果返回：操作成功/失败 + 操作详情

class BaseConfidenceCalcTool:
    """基础置信分计算工具"""

    # 四档来源初始值
    SOURCE_INITIAL = {
        "风评问卷": 0.9,
        "AI对话提取": 0.6,
        "用户自述": 0.4,
        "默认值": 0.2
    }

    def calc(self, tag: str, source: str, evidence_count: int,
             conflict_count: int, age_days: int) -> float:
        """
        计算单条标签的置信分
        :param tag: 标签名
        :param source: 来源
        :param evidence_count: 证据累积次数
        :param conflict_count: 冲突次数
        :param age_days: 标签存在天数
        :return: 置信分 [0.0, 1.0]
        """
        base = self.SOURCE_INITIAL.get(source, 0.2)
        # 证据累积增益（每次+0.05，上限+0.3）
        gain = min(evidence_count * 0.05, 0.3)
        # 冲突惩罚（每次-0.1）
        penalty = conflict_count * 0.1
        # 时间衰减（每年衰减20%）
        decay = max(0, 1 - age_days / 365 * 0.2)
        # 综合计算
        score = (base + gain - penalty) * decay
        # 边界钳制 [0.0, 1.0]
        return max(0.0, min(1.0, score))

    def batch_calc(self, tags: list) -> list:
        """批量计算置信分"""
        return [self.calc(**tag) for tag in tags]

class FinalConfidenceRankTool:
    """综合置信分重排工具"""

    # 4种场景权重配置
    SCENARIO_WEIGHTS = {
        "产品推荐": {"semantic": 0.3, "timeliness": 0.2, "accuracy": 0.25, "base": 0.15, "conflict": 0.1},
        "风险研判": {"semantic": 0.15, "timeliness": 0.3, "accuracy": 0.25, "base": 0.2, "conflict": 0.1},
        "客户画像": {"semantic": 0.2, "timeliness": 0.25, "accuracy": 0.2, "base": 0.25, "conflict": 0.1},
        "知识检索": {"semantic": 0.35, "timeliness": 0.15, "accuracy": 0.2, "base": 0.2, "conflict": 0.1}
    }

    def rank(self, memory_units: list, scenario: str) -> list:
        """
        综合重排记忆单元
        :param memory_units: 记忆单元列表
        :param scenario: 场景名称
        :return: 排序后的记忆单元列表
        """
        weights = self.SCENARIO_WEIGHTS.get(scenario, self.SCENARIO_WEIGHTS["知识检索"])
        for unit in memory_units:
            # 5个因子计算
            semantic_score = unit.get("semantic_similarity", 0.5)
            timeliness_score = self._calc_timeliness(unit.get("age_days", 0))
            accuracy_score = unit.get("historical_accuracy", 0.5)
            base_score = unit.get("confidence_score", 0.5)
            conflict_penalty = unit.get("conflict_count", 0) * 0.1

            final_score = (
                weights["semantic"] * semantic_score +
                weights["timeliness"] * timeliness_score +
                weights["accuracy"] * accuracy_score +
                weights["base"] * base_score -
                weights["conflict"] * conflict_penalty
            )
            unit["final_score"] = max(0.0, min(1.0, final_score))

        return sorted(memory_units, key=lambda x: x["final_score"], reverse=True)

class MemoryUnitValidator:
    """记忆单元校验器 — 六维属性校验"""

    VALID_RISK_LEVELS = ["保守型", "稳健型", "平衡型", "进取型", "激进型"]
    VALID_PRODUCT_TYPES = ["货币基金", "债券基金", "混合基金", "股票基金", "银行理财", "保险产品", "信托产品", "结构性存款"]
    VALID_INCOME_RANGES = ["10万以下", "10-50万", "50-100万", "100-500万", "500万以上"]

    def validate(self, unit: dict) -> dict:
        """
        校验记忆单元合法性
        :return: {"valid": True/False, "errors": [...]}
        """
        errors = []

        # 1. 枚举值合法性校验
        if unit.get("risk_level") and unit["risk_level"] not in self.VALID_RISK_LEVELS:
            errors.append(f"无效风险等级: {unit['risk_level']}")
        if unit.get("product_type") and unit["product_type"] not in self.VALID_PRODUCT_TYPES:
            errors.append(f"无效产品类型: {unit['product_type']}")

        # 2. 数值范围校验
        if unit.get("risk_score") is not None:
            if not (0 <= unit["risk_score"] <= 100):
                errors.append(f"风险评分超出范围: {unit['risk_score']}")
        if unit.get("confidence_score") is not None:
            if not (0.0 <= unit["confidence_score"] <= 1.0):
                errors.append(f"置信度超出范围: {unit['confidence_score']}")

        # 3. 时间逻辑校验
        if unit.get("create_time") and unit.get("update_time"):
            if unit["update_time"] < unit["create_time"]:
                errors.append("更新时间早于创建时间")

        return {"valid": len(errors) == 0, "errors": errors}

6.4 核心Tool清单与接口定义

以下是系统需要实现的所有核心Tool，按功能分组说明。

6.4.1 记忆体系相关

1. MemoryValidator — 记忆单元校验

项目说明
入参memory_unit (dict)：待校验的记忆单元
出参is_valid (bool)：是否合法；error_msg (str)：错误信息
说明校验记忆单元的结构完整性、字段合法性

2. BaseConfidenceCalc — 基础置信分计算

项目说明
入参source_type (str)：信息来源类型；evidence_count (int)：佐证数量；conflict_count (int)：冲突数量；months_since_verify (int)：距上次验证月数
出参base_confidence (float)：基础置信分；calc_detail (dict)：计算过程详情
说明根据多维权重计算单条记忆的置信度得分

3. FinalConfidenceRank — 综合置信度重排

项目说明
入参recall_memories (list)：召回的记忆列表；scene_type (str)：当前场景类型
出参ranked_memories (list)：重排后的记忆列表
说明结合场景对召回记忆进行综合排序

6.4.2 知识检索相关

4. KnowledgeRetrieval — RAG知识检索

项目说明
入参query (str)：检索查询；top_k (int)：返回条数；min_score (float)：最低相似度；knowledge_type (str)：知识类型筛选
出参results (list)：每项含content（内容）、score（得分）、source（来源）
说明基于向量相似度的知识库检索

5. GraphQuery — 图谱查询

项目说明
入参entities (list)：实体列表；query_type (str)：查询类型；max_hops (int)：最大跳数
出参paths (list)：关系路径；entities (list)：关联实体
说明在Neo4j中进行多跳关系查询

6.4.3 数据分析与操作相关

6. NL2SQL — 自然语言转SQL

项目说明
入参query (str)：自然语言查询；customer_id (str)：客户ID；context (dict)：上下文
出参sql_statement (str)：生成的SQL；query_result (list)：查询结果；interpretation (str)：结果解读
说明将自然语言转为SQL并执行，返回结果和解读

7. NL2API — 自然语言转API调用

项目说明
入参command (str)：自然语言指令；operator_id (str)：操作员ID；customer_id (str)：客户ID
出参api_name (str)：匹配的API名称；api_params (dict)：API参数；execution_result (dict)：执行结果；status (str)：状态
说明将自然语言指令转为具体的API调用并执行

6.4.4 风控与画像相关

8. RiskRuleMatch — 风控规则匹配

项目说明
入参transaction_event (dict)：交易事件数据
出参triggered_rules (list)：触发的规则列表；risk_level (str)：风险等级；confidence (float)：置信度
说明对交易事件进行规则匹配，输出风险等级

9. ProfileExtract — 画像标签提取

项目说明
入参dialogue_content (str)：对话内容；customer_id (str)：客户ID
出参extracted_tags (list)：提取的标签列表；confidence_scores (dict)：各标签的置信度
说明从对话内容中提取客户画像标签

10. SuitabilityCheck — 适当性匹配检查

项目说明
入参customer_id (str)：客户ID；product_id (str)：产品ID
出参is_suitable (bool)：是否匹配；risk_level_match (dict)：风险等级匹配详情；need_disclosure (bool)：是否需要额外披露
说明检查客户风险等级与产品风险等级是否匹配
