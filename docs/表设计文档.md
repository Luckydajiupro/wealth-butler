# 智能财富管家系统 — 表设计文档

## 0. 文档说明

- 本文档是《智能财富管家系统-项目需求文档.md》§6数据需求的**字段级展开**（该节6.1末尾已注明"详细字段设计放在独立的《表设计文档》中展开"），不新增业务规则，所有字段含义均可追溯到需求文档§3/§5/§6或《待确认疑点补充设计建议.md》。
- 覆盖项目实际用到的**全部4种数据存储**：MySQL（10张业务表，声明式建表）、Redis（缓存+事件总线）、Neo4j（知识图谱）、Milvus（向量检索，4个集合），以及MinIO（对象存储，非"表"但补充说明桶/对象命名规范）。
- MySQL建表遵循脚手架`BaseDBModel`声明式模式（`Repository/base/baseDBModel.py`）：Pydantic模型 + `create_table_sql`（ClassVar，手动SQL），`_ensure_table_exists()`自动建表，`_ensure_columns_exist()`自动`ALTER TABLE`补列——后续加字段只需改Pydantic模型和`create_table_sql`，无需手写迁移脚本。字段名反引号包裹，VALUES走`%s`参数化（SQL注入安全边界见下方"安全说明"）。
- 本文档写作时**顺带拍板了2处需求文档遗留的开放项**，拍板依据写在对应表下方：
  1. `base_user.user_type`（客户/员工）：独立列，不用`extra_data` JSON（需求文档3.4节"二选一在开发计划阶段拍板"，本文档给出结论）。
  2. 中期记忆（画像类记忆单元）落地位置：复用`fin_customer_profile`新增`memory_units`字段，**不新建`fin_memory_unit`表**（采纳《待确认疑点补充设计建议.md》2b节"能少建表就少建"的建议，10张表总数不变）；长期记忆（语义检索）需要一个Milvus集合，需求文档6.4节未列出，本文档在§4新增`fin_customer_memory_collection`补齐。
- 安全说明：脚手架`BaseDBModel`的CRUD方法对**字段名**做反引号拼接、对**字段值**做`%s`参数化，字段值层面无SQL注入风险；表名/字段名不经过用户输入拼接（均为代码里硬编码的Pydantic字段名），因此不构成新的注入面。NL2SQL工具生成的SQL需要走独立的安全校验层（见需求文档§7.2 NL2SQL安全校验层），不在本文档讨论范围。

## 1. MySQL 业务表设计（10张）

### 1.1 `base_user`（复用脚手架 + 理财业务扩展）

```sql
CREATE TABLE `base_user` (
  `id` INT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `username` VARCHAR(50) NOT NULL COMMENT '登录名（客户/员工统一登录）',
  `email` VARCHAR(100) COMMENT '邮箱',
  `phone` VARCHAR(20) COMMENT '手机号',
  `password_hash` VARCHAR(255) NOT NULL COMMENT '密码哈希',
  `source_module` VARCHAR(50) NOT NULL DEFAULT 'fin' COMMENT '来源模块标识（脚手架原字段，本项目固定为fin）',
  `status` ENUM('active','inactive','banned') DEFAULT 'active' COMMENT '账户状态（脚手架原字段）',
  `last_login_at` DATETIME COMMENT '最后登录时间',
  `extra_data` JSON COMMENT '扩展数据（脚手架原字段，本项目不用它承载user_type，理由见下）',
  `user_type` ENUM('CUSTOMER','EMPLOYEE') NOT NULL DEFAULT 'CUSTOMER' COMMENT '用户大类（新增字段，见下方"拍板说明"）',
  `employee_role` ENUM('理财顾问','风控专员','客户经理','业务管理员') COMMENT '员工主角色（新增，需求文档3.4节，单值），用于登录路由分发"进哪个Agent"（业务流程说明.md）；user_type=CUSTOMER时为NULL。角色非互斥可多角色叠加这件事不靠本字段存数组，而是靠下方1.1a节复用的base_role/base_user_role多对多关联表承载，本字段只存主角色用于快速路由，细粒度权限判断一律走base_user_role',
  `advisor_level` ENUM('初级','中级','高级') COMMENT '理财顾问执业等级（新增），决定可销售产品风险等级上限：初级→R1-R2，中级→R1-R3，高级→R1-R5（需求文档3.2节）；仅employee_role="理财顾问"时有值',
  `customer_level` ENUM('普通','金卡','白金','钻石','私行') DEFAULT '普通' COMMENT '客户等级（新增，需求文档3.1/3.4节）。与risk_level(C1-C5)是两套独立分层；本项目第一版仅作展示字段（人设/demo话术风格），不驱动适当性匹配或权限判断（4天工期取舍，原文有完整服务分层规则但未实现，见需求文档3.1节说明）',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted_at` DATETIME COMMENT '软删除时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  UNIQUE KEY `uk_email` (`email`),
  KEY `idx_phone` (`phone`),
  KEY `idx_source_module` (`source_module`),
  KEY `idx_status` (`status`),
  KEY `idx_deleted_at` (`deleted_at`),
  KEY `idx_user_type` (`user_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表（复用+扩展）';
```

**拍板说明（user_type独立列 vs extra_data JSON）**：`user_type`是RBAC鉴权和路由分发的高频过滤条件——几乎每次请求都要判断"这是客户还是员工"，需要建索引、需要在`WHERE`里直接等值查询；放进`extra_data` JSON要么每次`JSON_EXTRACT`（索引失效、写法冗长），要么给JSON字段单独建虚拟列索引（增加复杂度，4天工期不划算），因此选独立列。

### 1.1a `base_role` / `base_user_role`（复用脚手架，结构不变）

需求文档3.3节明确"脚手架`RoleModel.create_role`/`UserRoleModel.grant_role`无需结构变动"，即11个业务权限的RBAC矩阵直接复用脚手架已有的`base_role`（`RoleModel`）+ `base_user_role`（`UserRoleModel`，多对多关联）两张表落地，不新建表、不改字段——本文档只在此列出复用范围，避免遗漏"项目实际用到的表"：

- **落地方式**：为"理财顾问/风控专员/客户经理/业务管理员"4个角色各调用一次`RoleModel.create_role()`写入`base_role`；员工登录时其账号在`base_user_role`里对应1~N条记录（一人可兼多角色，靠这张关联表而非`base_user.employee_role`承载）。
- **需在`Permission`常量类新增的11个业务权限字符串**（需求文档3.3节）：`product:query`、`product:recommend`、`operation:purchase`、`operation:redeem`、`operation:transfer`、`risk:reassess`、`customer:info_update`、`risk:suspicious_report`、`workorder:create`、`risk:override`、`data:nl2sql_query`。
- **`base_user.employee_role`与`base_user_role`的分工**：前者是单值展示/路由字段（决定登录后默认进哪个Agent工作台），后者是权限判断的唯一依据（`has_permission()`/`has_any_permission()`），两者不冲突但语义不同，业务逻辑层做权限校验一律查`base_user_role`，不查`employee_role`。

### 1.2 `fin_customer_profile`（客户画像主表，四维度加权版）

```sql
CREATE TABLE `fin_customer_profile` (
  `id` INT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `customer_id` INT NOT NULL COMMENT '客户ID，关联base_user.id',
  `risk_level` ENUM('C1','C2','C3','C4','C5') COMMENT '客户风险分级（引用自fin_risk_assessment最近一次评估结果）',
  `risk_score` DECIMAL(5,2) COMMENT '综合评分0-100（5.3节公式：dimension1×25%+dimension2×25%+dimension3×30%+dimension4×20%）',
  `dimension1_score` DECIMAL(5,2) COMMENT '维度一-基础属性分（满分25，年龄/学历/职业/收入/资产五项均分后换算，5.3节第五条）',
  `dimension2_score` DECIMAL(5,2) COMMENT '维度二-投资经验分（满分25，5.3节第四条权重25%）',
  `dimension3_score` DECIMAL(5,2) COMMENT '维度三-风险偏好分（满分30，5.3节权重30%，计算时读取fin_risk_assessment.total_score作为输入之一并换算，两表为引用关系）',
  `dimension4_score` DECIMAL(5,2) COMMENT '维度四-行为异常分（满分20，5.3节权重20%）',
  `fm_flags` JSON COMMENT '当前命中的硬性熔断标记数组，元素取值FM-01~FM-05（5.3节第九条，一旦满足强制限制不可人工绕过）',
  `asset_allocation` JSON COMMENT '资产配置画像（JSON，用于个性化推荐输入）',
  `product_preference` JSON COMMENT '产品偏好画像（JSON，用于个性化推荐输入）',
  `memory_units` JSON COMMENT '中期记忆单元数组（新增，见下方"拍板说明"），每个元素结构：{unit_id,tag,info_type(fact/opinion),content,source,confidence,evidence_count,conflict_count,recall_count,create_time,update_time,valid_until,status(active/demoted/archived)}，六维校验规则见需求文档5.4.3节',
  `confidence_score` DECIMAL(4,3) COMMENT '画像整体置信度（5.4.1节公式：来源初值+证据增益(+0.05/次上限0.3)-冲突惩罚(-0.1/次)，乘时间衰减年-20%）',
  `updated_reason` ENUM('定期','事件','行为','市场','人工触发') COMMENT '本次更新触发原因',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_customer_id` (`customer_id`),
  KEY `idx_risk_level` (`risk_level`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='客户画像主表';
```

**拍板说明（memory_units落地位置）**：《待确认疑点补充设计建议.md》2b节建议"不做独立归档表，直接复用`fin_customer_profile`或新增`fin_memory_unit`表"。本文档采纳前者——中期记忆本质是"画像类tag"，与`fin_customer_profile`天然同customer_id一对一，用JSON数组承载可避免多一张表的联调成本（4天工期约束），代价是查询单个记忆单元不如独立表灵活，但当前功能规模（客户量级为测试数据）可接受。若后续记忆单元数量膨胀导致行体积过大，可平滑拆分为独立表（`BaseDBModel`自动补列机制不受影响）。

> `fin_risk_assessment` 与 `fin_customer_profile` 是两张不同用途的表，不能合并：前者对应5.1节16题问卷（一次性、12个月有效期、用于适当性强合规判定），后者对应5.3节四维度模型（持续动态、用于画像与个性化推荐），两表是"引用"关系而非"重复"关系（见需求文档6.1节脚注）。

### 1.4 `fin_transaction`（交易流水表）

```sql
CREATE TABLE `fin_transaction` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',

  `transaction_time` DATETIME NOT NULL COMMENT '交易发生时间（用于RW-008非正常时段判定等时间维度规则）',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_customer_id` (`customer_id`),
  KEY `idx_product_id` (`product_id`),
  KEY `idx_transaction_type` (`transaction_type`),
  KEY `idx_transaction_time` (`transaction_time`),
  KEY `idx_counterparty_account` (`counterparty_account`),
  KEY `idx_device_fingerprint` (`device_fingerprint`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='交易流水表';
```

> 反洗钱字段（`is_cash`/`counterparty_*`/`payer_account_name`/`device_fingerprint`）是本文档新增的补充设计——需求文档5.2节只给了RW-001~020的规则描述文本，未落到字段。字段命名对齐规则触发条件原文表述，风控监测Agent的规则引擎实现时可直接按字段名取值，不需要二次解释。

### 1.7 `fin_risk_alert`（风控预警表）


## 2. Redis 键设计

Redis客户端为脚手架单例`RedisClient`（`Client/redisClient.py`），当前只封装了String的`get/set/delete`；**Hash/Set/Stream类操作需直接使用`redis_client.client`（原生redis-py客户端）**，不在`RedisClient`基础上二次封装（4天工期，够用即可，不做过度封装）。

| Key模式 | 数据结构 | 字段/成员说明 | TTL | 用途 |
|---|---|---|---|---|
| `session:{session_id}:messages` | List（`RPUSH`/`LRANGE`） | 每个元素为一条消息的JSON字符串`{role,content,timestamp}` | 30分钟，最长24小时 | 短期会话记忆（客服Agent） |
| `profile:{customer_id}` | String（JSON序列化整行`fin_customer_profile`） | 见1.2节字段 | 7天 | 画像缓存（Cache-Aside，MySQL为准） |
| `product:list:{type}` | String（JSON数组） | 该`product_type`下产品列表 | 按需（产品变更时主动失效） | 产品列表缓存 |
| `product:detail:{id}` | String（JSON） | 单个`fin_product`行 | 按需 | 产品详情缓存 |
| `risk:alert:pending`（Set） | Set（`SADD`/`SMEMBERS`） | 成员为待处理`fin_risk_alert.id` | 常驻 | 待处理预警快速统计（避免每次COUNT查MySQL） |
| `stream:{event_type}`（Streams） | Stream（`XADD`/`XREADGROUP`/`XACK`） | Field-Value：`event_type/source_agent/payload(JSON字符串)/timestamp/trace_id`（见需求文档7.3节，`event_type`取值如`suspicious_intent`/`risk_alert`/`large_transaction`） | 持久化直至消费者ACK，未ACK消息保留在PEL | 跨Agent事件总线 |
| `nl2sql:cache:{query_hash}` | String（JSON，`query_hash`=自然语言问题的哈希） | `{sql,result,generated_at}` | 10分钟 | NL2SQL结果缓存，减少重复生成SQL的LLM调用 |
| `confirm_token:{token}` | String（JSON，`token`=UUID4） | `{customer_id,action_type,params,status,requested_by,created_at}`，`status`取值`待确认\|已确认\|执行\|已取消`（见《Agent设计文档.md》§5.4） | 10分钟 | 业务操作Agent二次确认状态机（ADR-4），申购>1万/转账>5万触发 |

## 3. Neo4j 图谱模型

### 3.1 节点

| 节点标签 | 关键属性 | 数据来源 |
|---|---|---|
| `Customer` | customer_id（对齐base_user.id）、name、risk_level | MySQL导入 |

| `RiskLevel` | level（C1-C5或R1-R5，按连接的节点类型区分客户风险等级/产品风险等级） | 静态字典节点 |

### 3.2 关系

| 关系类型 | 方向 | 属性 | 用途 |
|---|---|---|---|
| `HAS_RISK_LEVEL` | Customer→RiskLevel | — | 客户当前风险分级 |
| `INVESTS_IN` | Customer→Product | shares、market_value（对齐fin_holdings） | 持仓关系，供GraphRAG/多因子排序查询 |
| `BELONGS_TO` | Product→Industry | — | 产品所属行业，供投顾助手`calc_graph_signal`计算行业集中度（《待确认疑点补充设计建议.md》疑点4） |
| `MANAGED_BY` | Product→FundManager | — | 管理人信息 |

| `LOCATED_IN` | Industry→Market | — | 行业所属市场 |
| `RELATED_TO` | Customer→Customer | relation_type（家庭成员/同一控制人/共用设备等） | 关联账户识别，支撑RW-005/RW-010/RW-018关联交易类规则；关系数据需在测试数据中额外构造 |

## 4. Milvus 向量集合设计

复用脚手架`BaseVDBModel`模式（`Repository/base/baseVDB.py`）：Pydantic模型字段通过`json_schema_extra`声明`is_primary`/`auto_id`/`max_length`/`dim`/`is_sparse_vector`等元信息，`_check_and_create_collection()`按模型字段自动生成Schema并建集合建索引，密集向量默认HNSW/COSINE（`M=8, efConstruction=64`），稀疏向量默认`SPARSE_INVERTED_INDEX`/BM25。统一Embedding模型：本地 Ollama bge-m3（1024维，与各集合`dim=1024`一致）。

| 集合 | 用途 | 关键字段 | 索引/检索方式 | TopK/阈值 |
|---|---|---|---|---|
| `fin_faq_collection` | FAQ问答对（客服Agent RAG） | `id`(主键,auto_id)、`question`(VARCHAR,启用match+analyzer)、`answer`(VARCHAR)、`embedding`(FLOAT_VECTOR,dim=1024) | HNSW/COSINE，纯稠密向量检索 | TopK3，阈值0.75 |
| `fin_product_collection` | 产品说明文档切块（客服/投顾检索产品知识） | `id`、`product_id`(关联fin_product.id)、`content`(VARCHAR,启用match+analyzer)、`embedding`(FLOAT_VECTOR,dim=1024)、`content_sparse`(SPARSE_FLOAT_VECTOR,由content经BM25函数生成) | 混合检索（稠密0.7+BM25稀疏0.3加权融合，参照`VdbLLMConversation.get_n_high_similarity_item`写法） | TopK5，阈值0.7 |
| `fin_policy_collection` | 金融政策法规切块（适当性/反洗钱规则原文检索） | 同`fin_product_collection`结构，`product_id`替换为`policy_source`(VARCHAR,政策文件名) | 同上混合检索 | TopK5，阈值0.7 |
| `fin_customer_memory_collection`（补充设计，见§0） | 客户长期记忆语义检索（对应"短期→中期→长期"三级记忆召回的长期一环，MemoryStore.search()长期分支：Milvus向量检索+Neo4j图谱关联） | `id`、`customer_id`(VARCHAR,过滤用)、`memory_unit_id`(VARCHAR,对齐fin_customer_profile.memory_units里的unit_id)、`content`(VARCHAR,记忆内容原文)、`embedding`(FLOAT_VECTOR,dim=1024) | HNSW/COSINE，按`customer_id`过滤后检索，参照`VdbLLMConversation`按user_id/session_id过滤的写法 | TopK5，阈值0.6（长期记忆召回容忍度略低于FAQ，避免漏检） |

> `fin_customer_memory_collection`不是需求文档6.4节原有内容，是本文档为补齐"长期记忆"存储位置新增的第4个集合（依据：《待确认疑点补充设计建议.md》2b节`MemoryStore.search()`明确写了"长期: Milvus向量检索(query做embedding) + Neo4j图谱关联"，但6.4节漏列了对应集合）。写入时机：`fin_customer_profile.memory_units`中`status`从`active`降级为`archived`时，同步把该条记忆embedding后写入本集合，实现热数据（MySQL JSON，近期高频访问）与冷数据（Milvus向量，长尾语义检索）分层。
