> 分析对象：`D:\lqh\reproject\ric-train\ric-train\Base`（通用Python/FastAPI后端脚手架）。目的：判断4天工期内，哪些能力可以直接复用/简单配置即用，哪些必须从零新写，用于制定开发计划和需求文档的架构章节。

## 一、脚手架总体架构

分层：`Api`(FastAPI路由) → `Service`(业务逻辑) → `Ai`(LLM/Agent框架) → `Client`/`Repository`(DB连接与ORM/VDB抽象) → `Models`(具体表模型)。

- **Repository层**：`BaseDBModel`（Pydantic+ABC的MySQL ORM，首次访问自动建表、自动diff字段并`ALTER TABLE`补列，加字段近乎零成本）；`BaseVDBModel`（Milvus ORM，通过Pydantic字段的`json_schema_extra`自动生成CollectionSchema并自动建集合建索引，内置`hybrid_search()`稠密+稀疏BM25混合检索）。
- **Agent执行范式**：`BaseAgent(ABC)` + 三种具体范式子类 `ReActAgent`/`CoTAgent`/`PlanAndExecuteAgent`，接收`llm/tools/memory/middlewares`。工具体系`BaseTool.to_openai_schema()`自动从Pydantic生成Function Calling schema。
- **中间件洋葱模型**：`AgentContext` + `Middleware(ABC)` + `MiddlewareChain`，内置`Logging→Metrics→Safety→Eval`四个中间件，通过`BaseAgent(middlewares=[...])`注入。
- **LLM抽象层**：`QwenLlm`/`DeepSeekLlm`均为OpenAI SDK兼容实现，支持流式与Function Calling；Qwen独有OCR/ASR/Embedding(1024维)。**（本项目嵌入改走本地 Ollama bge-m3，封装见`Base/Ai/llms/ollamaEmbedding.py`，依据见需求文档§2.5）**

## 三、关键复用点细节

1. **`nl2cypherAgent.py` 不能直接改造为GraphRAG查询能力**——现有实现方向相反，做的是"自然语言→抽取实体关系→写入Neo4j"（知识入库），不是查询。可复用的是ReActAgent双工具模式、`_run_loop`重写技巧、`Neo4jClient.run(cypher, parameters)`执行原语。**GraphRAG的多跳查询Agent需要新写**，预估1~1.5人天。
2. **Milvus RAG成本极低**——仿照`VdbLLMConversation`的写法定义新的`BaseVDBModel`子类即可，配置即用。
3. **NL2SQL无先例可循**——`neo4jService.parse_nl_2_graph`的"LLM生成结构化JSON→解析重试"模式可迁移为架构骨架，`MySQLClient.SQLBuilder`可作安全拼装后端，但**SQLBuilder不做表名/字段名白名单**，`ToolGuard`的危险操作拦截只是关键词子串匹配（可被注释、大小写变形绕过）。**NL2SQL安全校验必须完全新写**。
4. **用户表**：`UserModel`(`base_user`)无`employee_role`/`customer_level`字段，建议直接给现有表加两列（成本分钟级），而不是另建`sys_user`平行表。RBAC结构本身不需要改动，"理财顾问/风控专员/客户经理"直接作为新增`RoleModel`记录，需要往`Permission`常量类补充业务权限字符串（如`risk:override`）。
5. **MemoryV1Service**：`get_simple_memory`三源合并(DB近N轮+VDB相似检索+会话摘要)的"多源组合"模式与目标项目三层记忆架构相似，`get_n_high_similarity_item`、`ai_summary_session`可作为模板改造。但**置信度公式体系(证据积累/冲突惩罚/时间衰减)零覆盖**，现状唯一近似的是写死的`distance>0.5`单一阈值。

## 四、完全空白、必须新写的部分

- 风控规则引擎（`ToolGuard`只是简单黑名单，非可配置规则引擎）
- 适当性匹配逻辑（客户风险等级 vs 产品风险等级）
- NL2SQL安全校验（表/字段白名单，需基于白名单或AST方案）
- 客户画像四维度评分算法
- 置信度计算公式体系（证据积累/冲突惩罚/时间衰减）
- 跨Agent Redis Streams事件总线（RedisClient无Pub/Sub也无Streams封装；已从Pub/Sub改为Streams，见需求文档2.4节"设计取舍"）
- 8个业务操作Function Calling工具的具体业务逻辑
- 10张业务数据表的表结构设计与业务逻辑
- 人机协同二次确认状态机（SafetyMiddleware只有"通过/阻断/脱敏"，无"待确认→已确认→执行"状态）
- 多Agent协作编排层（现状都是独立单体Agent，无supervisor/路由/通信机制）
- trace_id链路追踪字段（成本低，但目前不存在）
