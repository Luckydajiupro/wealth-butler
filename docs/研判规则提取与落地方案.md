# 智能财富管家系统 — 用户研判规则提取与落地方案

## 0. 文档说明

- 覆盖范围：`用户研判规则/`目录下2个文件——《反洗钱可疑交易识别规则.md》（20条规则RW-001~020）、《投资者风险画像研判规则.md》（四维度加权打分模型+5条硬性熔断规则FM-01~05）。
- 与《RAG切片入库策略.md》的本质区别：那份文档解决"文本→向量，供语义检索"；本文档解决**"表格里的阈值数字→规则引擎能直接执行的参数"**，服务对象是风控监测Agent（F4.1）的规则引擎，不是靠相似度检索，而是要100%精确匹配触发条件——语义检索阈值0.7不保证命中，拿检索结果去做"金额≥50000"这种业务判断是不可靠的，所以这两份文件的核心内容必须走结构化提取，不能只做RAG化了事。
- 已有决策基础（本文档不重新设计，直接对齐）：
  - 《待确认疑点补充设计建议.md》疑点1已给出置信度公式`confidence = min(1.0, Σ规则权重 + 0.15×is_repeat)`，以及🔴🟠🟡🔵→强/中/弱权重档位（0.35/0.20/0.10）的映射方向；
  - 《表设计文档.md》`fin_risk_alert`表已预留`alert_type`/`rule_weight_tier`/`confidence`/`is_repeat`/`repeat_trigger_count`/`is_false_positive`字段，`fin_customer_profile`表已预留`dimension1_score`~`dimension4_score`/`risk_score`/`fm_flags`字段，`fin_transaction`表已预留`is_cash`/`counterparty_account`/`counterparty_name`/`counterparty_region`/`payer_account_name`/`device_fingerprint`字段——本文档要做的是把20条规则和打分表逐条对应到这些已经存在的字段上，不新增表、不新增字段。
- **双轨提取原则**：规则的**阈值参数**走本文档§2/§3的结构化提取（驱动规则引擎自动判断）；规则的**原文条款**（自然语言描述的触发条件、处理建议）同时追加进`fin_policy_collection`（详见§4），供风控专员/合规人员用客服Agent做"这条规则具体怎么判定的"解释性检索。两条路径服务不同场景，不互斥，不能只做一个。
- **拍板说明（规则定义要不要落MySQL）**：不新建表，规则定义（编号/阈值/权重档位/打分区间）留在代码常量字典+JSON配置文件里，只有**规则执行结果**落MySQL（`fin_risk_alert.alert_type`存命中的RW编号、`fin_customer_profile.fm_flags`存命中的FM标记）。理由：①规则触发条件本身是跨表聚合/关联查询，DB表能存的只有阈值参数，JSON配置文件已经解决"参数与代码分离、可调"的诉求，建表是重复方案；②会打破§0已引用的"10张业务表不新增"边界（`fin_memory_unit`是否新建时用同一理由否决过）；③4天工期没有规划规则管理后台，DB化"不改代码调阈值"的收益在没有管理界面时无法兑现，改JSON和改DB一行工作量相同，JSON还能被git追踪变更历史。

## 1. 为什么不新建MySQL规则表，而是"代码化规则函数 + 参数外置"

20条反洗钱规则的触发条件复杂度差异很大：

- 简单单表比较：RW-001（单日现金交易≥5万）；
- 时间窗口聚合：RW-002（7日内笔数+金额）、RW-008（凌晨时段+90天基线对比）；
- 跨账户关联：RW-004/RW-005（多个来源账户集中/分散）、RW-018（同一身份证/手机号/设备指纹关联的多账户归集）。

用纯声明式JSON表达式在4天内做一个通用的规则解释引擎不现实，且违反项目一贯的"能少建表就少建"原则（表设计文档§0已用同样理由否决了`fin_memory_unit`独立表）。因此采用规则引擎领域的常见轻量做法：

- **规则元数据**（编号/名称/类型/风险等级/权重档位）整理成风控监测Agent代码里的一个常量字典（如`AML_RULES: dict[str, RuleMeta]`），作为"规则引擎判断逻辑"和"写入`fin_risk_alert`"两处共享的唯一事实来源，避免文档编号和代码判断逻辑对不上。
- **触发条件本身**是Python函数（如`def check_rw001(customer_id, window) -> RuleHit | None`），阈值数字（50000/20次/90%等）作为函数参数的默认值，来源于§2.2表格，不是散落在if语句里的裸数字——联调阶段按测试数据调优阈值时，只改这一处。

投资者画像的打分表（区间→分值的查找表，如"年龄26-35岁→10分"）规整度更高，不涉及跨表聚合，更适合做成独立的**声明式JSON/YAML配置文件**（如`profile_scoring_rules.json`），由打分函数加载读取，理由和实现方式见§3.1。

### 2.2 规则命中 → 写入`fin_risk_alert`的映射

规则引擎跑完一批规则后，对命中的客户按以下逻辑写入`fin_risk_alert`一行：

| `fin_risk_alert`字段 | 取值逻辑 |
|---|---|
| `alert_type` | 触发规则编号，如"RW-004"（单规则触发写单条，同一客户同批触发多条规则各自写一行，`transaction_ids`可交叉引用同一批流水） |
| `rule_weight_tier` | 查`AML_RULES[rule_id].weight_tier`（§2.1表最后一列） |
| `confidence` | `min(1.0, Σ本次触发规则权重 + 0.15×is_repeat)`（疑点1原文公式，`Σ`在"多条规则合并预警"场景下对多条weight求和） |
| `is_repeat` | 查该客户+该规则编号30天内是否已有历史`fin_risk_alert`记录 |
| `repeat_trigger_count` | 30天内同客户+同规则编号的命中次数计数 |
| `alert_level` | 按规则原文第三章：1条规则→蓝，2-3条或重复触发→黄，>3条→红（与confidence是独立维度，不能混用同一套阈值） |

### 2.3 优先级、冲突处理、误报处理的提取（第三章/第四章）

- **规则优先级**（原文第四条5档优先级表）→ 提取为`AML_RULES`字典里每条规则的`priority`字段（1-5），用于"同一交易触发多条规则时调查顺序"的排序逻辑，与权重档位是两个独立属性（优先级决定"先查哪个"，权重决定"置信度贡献多少"）。
- **升级机制**（第五条"30天内累计触发≥3次中风险预警自动升级为高风险客户"）→ 提取为一条独立的批处理规则，读取`fin_risk_alert`按客户+30天窗口聚合`alert_level='黄'`的计数，命中后更新客户风控标记（建议复用`fin_customer_profile.fm_flags`，追加一个业务自定义标记而非FM-01~05，或在客户画像上加一个"风控关注名单"布尔位——具体落点留待联调阶段与同学D共同确认，本文档只提取规则本身）。
- **误报判定标准**（第六条5类误报情形）→ 提取为风控专员处理`fin_risk_alert`时的**处理指引文本**（人工判断辅助，不是自动化规则），随预警工单一起展示；`is_false_positive`字段由风控专员人工标记，规则引擎不自动判定误报。
- **误报率考核指标**（第八条：总体<70%、高风险<30%、平均耗时<2小时）→ 不是提取到规则引擎的内容，是运营监控指标，建议作为数据分析Agent（F2.3）的一个统计查询场景（NL2SQL能回答"上月反洗钱预警误报率是多少"），提取到本文档只是为了标注这个信息的正确归属，不在风控Agent本身实现。

### 2.4 复杂关联规则的实现建议

RW-004/005/010/018这几条规则的触发条件本质是"账户之间的关系"（多来源账户、对手方集中度、同一身份证/手机号/设备指纹关联多账户），单纯查`fin_transaction`表在SQL里用`GROUP BY counterparty_account`能做，但"同一身份证/手机号/设备指纹关联的账户"这种**实体关联查询**用Neo4j图查询更自然（项目已有Neo4j知识图谱层，参见表设计文档§3）。建议：

- RW-004/005/010（对手方账号维度的集中度）：`fin_transaction.counterparty_account`字段上直接SQL聚合即可，不需要Neo4j。
- RW-018（同一身份证/手机号/设备指纹关联多账户）：如果Neo4j图谱里已经建了客户实体间的关联关系（如共享设备指纹），直接查图更简洁；如果图谱暂未建这类关系，MVP阶段可退化为SQL按`device_fingerprint`在`fin_transaction`表上直接`GROUP BY`查询，效果等价，只是失去了"关系可视化"的附加价值——4天工期建议先用SQL兜底，图查询作为增强项。

## 3. 投资者风险画像研判规则提取方案

### 3.1 四维度打分表 → 声明式配置文件

《投资者风险画像研判规则.md》第二章的10张打分表（年龄/学历/职业/年收入/资产规模/投资年限/产品复杂度/交易频率/历史收益/风险测评映射/情绪化扣分/亏损承受调整）结构高度规整（都是"区间→分值"），提取为一份`profile_scoring_rules.json`配置文件，按维度分组存放区间-分值映射，打分函数按客户实际值查表取分再套第五~八条给出的加权公式：

```
维度一得分 = (年龄分+学历分+职业分+收入分+资产分) ÷ 5 ÷ 10 × 25
维度二得分 = (投资年限分+产品类型分+交易频率分+历史收益分) ÷ 4 ÷ 10 × 25
维度三得分 = 风险测评得分(问卷换算) + 情绪化交易扣分 + 亏损承受调整（钳制0-30）
维度四得分 = 异常行为计分（满分20，按第八条异常行为数量分档）
综合得分 = 维度一×25% + 维度二×25% + 维度三×30% + 维度四×20%
```

配置文件与计算公式分离的好处：阈值分档（如"26-35岁→10分"）后续联调时按测试数据调整，只改JSON，不碰计算逻辑代码——这与AML规则"参数外置"是同一套设计思路。

### 3.2 原始输入字段缺口与解决方案（需在开发阶段确认）

核对发现：`base_user`和`fin_customer_profile`都**没有**存储维度一所需的年龄/学历/职业/年收入/资产规模原始值，也没有RW-013(PEP标记)/RW-016(年龄)/RW-006(申报年收入)这几条AML规则需要的客户属性字段。这是一个需要在开发阶段确认数据来源的缺口，本文档给出建议方案而非新增表/字段（保持10张表不变）：

- **复用`fin_risk_assessment.answers`**：需求文档5.1节明确16题风评问卷本身就包含"年龄10%/收入状况20%/资产规模20%/投资经验20%/风险承受能力20%/投资目标10%"六个维度的题目作答，`fin_risk_assessment.answers`（JSON，逐题作答记录）大概率已经覆盖了年龄/收入区间/资产规模区间/投资经验这几项——四维度模型的维度一（年龄/收入/资产）和维度二（投资年限）的原始输入，建议直接解析这份JSON取值，不用另存一份。
- **学历/职业**：16题问卷若未单独问（问卷聚焦监管要求的风险因子，不一定覆盖学历/职业），按《投资者风险画像研判规则.md》**第十四条"信息不完整处理"**的既有设计处理——这条规则本身就是为了解决"部分维度数据缺失"场景设计的，直接复用即可：学历/职业信息缺失时不强行拒绝评分，给保守默认分（如学历默认按"大专"6分、职业默认按"中小企业员工"6分计算），不需要额外产品设计。
- **PEP标记（RW-013）**：项目测试数据规模小（`用户测试数据/`目录2个客户画像样本），建议作为`fin_customer_profile`人工可维护的一个业务标记（可复用`asset_allocation`或新增极小的JSON键，不新建列），MVP阶段允许由风控专员在工单里人工勾选后写入，不强求自动化识别（PEP名单比对本身需要外部数据源，不在4天工期范围）。

### 3.3 硬性熔断规则（FM-01~05）提取

5条规则触发条件简单（年龄/资产/风评时效/身份状态/单日亏损的简单条件判断），直接函数化，每条一个独立函数，输出统一写入`fin_customer_profile.fm_flags`（JSON数组，元素取值FM-01~FM-05，与表设计文档字段定义完全一致）：

| 规则编号 | 触发条件（提炼） | 处理动作提取要点 |
|---|---|---|
| FM-01 | 年龄<18禁止开户；18-22购R4+需监护人同意；>70购R3+需当面签字；>80仅R1-R2 | 按年龄分4档，与产品风险等级联动，需在业务操作Agent(F3.4)申购校验时读取`fm_flags` |
| FM-02 | 无固定收入+资产<1万→仅R1-R2；无固定收入+资产1-5万→仅R1-R3(且R3≤30%仓位) | 触发后限制可购产品等级，仓位比例限制需要业务操作Agent额外校验持仓占比 |
| FM-03 | 风评超12个月未更新→冻结购买权限；超6个月→仅提醒 | 直接复用`fin_risk_assessment.valid_until`字段判断，不需要新字段 |
| FM-04 | 身份证过期超90天→冻结全部交易；联网核查不通过→暂停非柜面交易；涉制裁名单→立即冻结 | 需要身份证有效期字段（同§3.2缺口，建议同样走开发阶段确认，暂无对应列） |
| FM-05 | 单日亏损超10%→提示；连续3日赎回超40%→人工回访；疑似盗用→冻结账户 | 依赖`fin_holdings`/`fin_transaction`实时计算，属于运行时触发而非画像更新时触发，与FM-01~04（画像更新时判定）触发时机不同，需要在实现时区分 |

`fm_flags`一旦命中"不可人工绕过"（原文第九条），意味着业务操作Agent(F3.4)执行申购/赎回前必须读取该字段做强制拦截，这是F4.1（风控监测Agent写入）和F3.4（业务操作Agent读取校验）两个Agent之间的一个明确协作点，建议在开发计划里显式标出。

### 3.4 更新触发条件的提取（第十七条）

原文5种触发类型（定期/事件/行为/市场/人工）提取为画像重算的触发时机，对应到`fin_customer_profile.updated_reason`枚举值（表设计文档已定义该字段，取值与原文5种类型完全一致）：

| 触发类型 | 触发条件 | 建议实现方式 |
|---|---|---|
| 定期 | 风评到期前30天 | 定时任务扫描`fin_risk_assessment.valid_until` |
