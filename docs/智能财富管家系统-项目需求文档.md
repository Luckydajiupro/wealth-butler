## 1. 项目概述

### 1.1 项目背景与目标

XX科技拟建设"智能财富管家系统"，服务两类用户：**内部员工**（理财顾问、风控专员、客户经理）与**外部客户**（零售投资者、高净值客户）。项目要解决五类业务痛点：

1. 客户服务响应慢、话术不统一 → AI 7×24小时统一话术响应
2. 投顾凭经验人工研判客户画像、翻手册查产品 → AI自动生成画像+智能匹配产品
3. 风控人工抽查交易存在遗漏 → AI实时逐笔匹配规则、自动分级预警
4. 数据查询依赖IT工单写SQL → 自然语言NL2SQL自助查询
5. 业务操作需多系统切换 → NL2API一句话完成申购/赎回/转账等操作

**核心目标**：用5个垂直Agent（客服/投顾/风控/数据分析/业务操作）+ RAG/GraphRAG/NL2SQL/NL2API四大AI能力 + 三层记忆体系，替代人工客服、人工画像研判、人工风控抽查、人工写SQL、多系统切换操作，在**不突破适当性匹配、反洗钱等金融合规红线**的前提下提升效率、降低人力成本。

### 1.3 项目范围

**范围内**：客服/投顾/风控/数据分析/业务操作5大Agent；RAG知识库；GraphRAG知识图谱增强；NL2SQL自然语言查数；NL2API自然语言执行业务操作；客户画像与风险评估；风控规则引擎与预警；三层记忆体系与置信度计算；跨Agent事件协作；Mock身份认证。

**范围外（Out of Scope）**：真实支付通道对接、真实身份认证/短信验证码、移动端APP、生产级部署（K8s/CI-CD）；**基金/资管产品的实际投资运作**（基金经理选股调仓、交易员下单执行等资金池投资决策）——客户"申购/赎回"本质是把资金交给基金管理人集合运作，买卖的是基金份额，真正对这笔钱做投资决策、下单交易的是基金公司内部的基金经理与交易员团队，这不属于本系统（财富管理/客户服务端）的职责范围，业务操作Agent只模拟客户端提交份额申购/赎回请求、以及份额净值变化导致的持仓市值结果，不模拟资金的实际投向决策（[《公开募集证券投资基金运作管理办法》](http://www.csrc.gov.cn/csrc/c106256/c1653978/content.shtml)）。

## 2. 总体架构设计

### 2.1 系统总体架构（复用脚手架分层）

沿用脚手架 `Base` 包的既有分层，不另起一套架构：

```
Api          FastAPI路由层（复用 Api/ai/chatApi.py、Api/authApi.py 的既有模式，新增 5个Agent对话入口 + 业务功能路由）
   ↓
Service      业务逻辑层（复用 authService.py 等，新增 profileService/riskService/nl2sqlService/operationService/memoryService 等）
   ↓
Ai           LLM/Agent框架层（复用 BaseAgent + ReActAgent + 中间件链路，5个Agent均为其子类）
   ↓
Client/Repository   数据库连接与ORM/VDB抽象（MySQL/Redis/Milvus/Neo4j/MinIO客户端全部复用，Repository的BaseDBModel/BaseVDBModel自动建表建集合）
   ↓
Models       具体表模型（复用部分RBAC模型，新增10张业务表模型）
```

**多Agent编排层的落地位置**：F5.1要求的"编排层"不是分层图上新增的一层，而是Api路由层里`POST /api/chat`这一个端点内部的轻量分发逻辑——按请求体`agent_type`字段选择对应Agent实例处理本次请求，不做Agent间多跳调用或动态转交（详见《架构设计文档.md》ADR-6、逻辑架构图）。

### 2.2 五大Agent职责矩阵

| 维度 | 智能客服 | 投顾助手 | 风控监测 | 数据分析 | 业务操作 |
|---|---|---|---|---|---|
| 服务对象 | 客户 | 理财顾问 | 风控专员 | 内部员工 | 理财顾问、客户经理 |
| 核心能力 | 知识问答 | 产品推荐 | 异常检测 | NL2SQL查数 | NL2API执行操作 |
| 关键技术 | RAG+短期记忆 | GraphRAG+中期记忆 | 规则引擎+置信度 | NL2SQL | NL2API+RBAC |
| 触发方式 | 主动交互 | 主动交互 | **双轨被动触发**（实时/准实时规则：事件流触发；日批/周批规则：APScheduler定时批量扫描，见2.4节） | 主动交互 | 主动交互 |
| 安全等级 | 低（只读） | 中（涉及推荐） | 高（涉及预警） | 中（涉及数据） | 高（涉及写操作） |
| 脚手架基座 | `ReActAgent` + RAG工具（Milvus已现成） | `ReActAgent` + GraphQuery工具（需新写查询逻辑） | 独立规则引擎（不走Agent对话范式） | `ReActAgent` + NL2SQL工具（需新写安全层） | `ReActAgent` + Function Calling工具（外壳现成，逻辑需新写） |

> **客户实际只直接对话1个Agent**：5个Agent里只有智能客服Agent的服务对象是客户本人，投顾助手/业务操作/风控监测/数据分析这4个全部是员工侧工具，客户不直接触达。客户"了解产品→形成购买意向→下单/转账"的完整旅程中，只有第一步（产品咨询）在客服Agent里由客户自己完成；后续的产品推荐由理财顾问通过投顾助手Agent生成，申购/赎回/转账等实际写操作由理财顾问或客户经理通过业务操作Agent代客户执行——这两步都需要客户先触发客服Agent的"转人工"意图、自动生成客户转介工单被员工领取（Mock真实电话/线下联系，见2.4.1节），不存在客户直接对话投顾助手Agent或业务操作Agent的入口（详见3.2/4.3节、《业务流程说明.md》）。业务操作Agent的服务对象同时含理财顾问（申购/赎回/风评重做，见3.3节`operation:purchase`/`operation:redeem`权限归属）和客户经理（转账/信息更新/工单创建），此前版本遗漏了理财顾问这一半，已订正。

### 2.3 统一Agent执行骨架（复用+扩展）

老师原始设计要求所有Agent共享统一骨架（输入接收→短期记忆召回→中期记忆召回→长期记忆召回→意图路由→置信度重排→核心逻辑→工具调用→结果生成→流式输出→数据沉淀→事件广播），子类仅需实现 `classify_intent()`/`_get_handler()`/`_intent_threshold()`/`_scenario_name()` 四个方法。

**映射到脚手架的落地方案**：脚手架 `BaseAgent` 已提供 `llm/tools/memory/middlewares` 的统一构造与 `_run_loop`，中间件洋葱模型（`Logging→Metrics→Safety→Eval`）天然符合"骨架统一、策略可插拔"的设计诉求。改造点：

1. **记忆召回**：脚手架中间件链路里没有"记忆召回中间件"，需要新增一个 `MemoryRecallMiddleware`，在 `process_request` 阶段调用短期(Redis)/中期(MySQL+Redis)/长期(Milvus+Neo4j)记忆检索，参考 `MemoryV1Service.get_simple_memory` 的多源合并模式改造。
2. **意图路由与置信度阈值**：`classify_intent()`在各Agent的子类里实现，各Agent阈值遵循"操作风险越高阈值越高"原则排序——业务操作0.75最高（涉及资金写操作，出错代价最大）＞投顾0.65（涉及产品推荐，可能引发适当性问题）＞客服0.6（纯问答，出错代价小）＞数据分析0.5最低（内部只读查询，出错不造成业务后果），具体数值仍为团队拟定的示例值，非权威依据，需团队讨论确认或用测试用例调优，详见第10章第3项；数据分析/风控Agent的路由逻辑与客服/投顾/业务操作不同（前者要么单一路径要么被动触发），需要在子类里按需简化，不强行套用意图分类。
3. **事件广播**：中间件链路末尾新增事件发布钩子，对接第2.4节的事件总线（新建）。

### 2.4 跨Agent协作机制（新建）

Agent之间不直接调用，通过 **Redis Streams 事件总线**解耦（**已从Pub/Sub改为Streams**，见下方"设计取舍"）。**脚手架的 `RedisClient` 目前既无Pub/Sub也无Streams封装，需要基于redis-py原生`xadd`/`xreadgroup`/`xack`从零封装**（预估工作量：0.5~1人天）。

**设计取舍：为什么不用Pub/Sub**——Redis Pub/Sub是fire-and-forget，只保证"发布"不保证"送达和处理成功"。而下面定义的3类事件全部是驱动下游Agent核心业务逻辑的**必须处理**任务，不是"丢了也无所谓"的UI提醒——项目里也没有需要低延迟推送的仪表盘场景，理财顾问/客户经理的待办列表本来就是登录后查询`biz_work_order`得到（见2.4.1节），不依赖实时推送。因此统一改用Redis Streams的消费组模式，一套封装覆盖全部3类事件，不需要再为`risk_alert`单独设计"MySQL持久化+定时补偿扫描"的特殊逻辑，也不再需要Pub/Sub这个组件。项目按**单消费者、不横向扩容**的部署模型设计（每个Agent进程内一个固定消费组），因此不需要`XAUTOCLAIM`等面向多实例竞争消费的复杂重投逻辑，复杂度可控。

已定义事件类型（一类事件一个Stream）：
- `stream:risk_alert`（风控Agent生产）→ 投顾Agent消费更新客户风险标记；客服Agent消费标记高风险客户
- `stream:large_transaction`（业务操作Agent生产）→ 风控Agent消费，作为触发信号
- `stream:suspicious_intent`（客服Agent生产）→ 风控Agent消费，作为触发信号

事件消息字段：`event_type`/`source_agent`/`payload`(JSON字符串)/`timestamp`/`trace_id`。

**风控Agent的双轨触发机制**：RW-001~RW-020规则表（见5.2节）里每条规则都标注了执行频率——RW-001/003/008/011/014/015/016/017这8条是"实时/准实时"，其余12条（RW-002/004/005/006/007/009/010/012/013/018/019/020）是"日批/周批"。两者触发方式不同，不能都挂在事件流上：
- **实时/准实时规则**：由`consume()`收到`stream:large_transaction`/`stream:suspicious_intent`事件后触发评估。事件本身**只是触发信号**（携带`customer_id`/`transaction_id`等定位信息），风控Agent收到后直接按规则要求的时间窗口回查`fin_transaction`等源表判定，**不维护派生的Redis计数器状态**。这样处理天然幂等——查询没有副作用，即使因at-least-once投递重复触发同一次评估，结果也不会因为"计数漂移"而出错，比维护自增计数器更简单也更可靠。
- **日批/周批规则**：与事件流无关，走`Service/scheduler/`的APScheduler装饰器（见2.5节），按cron周期直接扫描`fin_transaction`等表做批量判定，命中同样写入`fin_risk_alert`+`biz_work_order`。

**封装为共享`EventBus`工具（`Ai/tools/eventBus.py`，新建）**：Streams的消费组创建/PEL重放/ACK这些细节全部封在`publish()`/`consume()`两个函数里，负责各个Agent的同学只需调用，不需要各自理解Streams内部机制，避免分工时每人抄一遍样板代码、在异常处理细节上跑偏：

```python
# --- Ai/tools/eventBus.py ---
def publish(event_type: str, source_agent: str, payload: dict, trace_id: str) -> None:
    redis_client.xadd(
        f"stream:{event_type}",
        {"event_type": event_type, "source_agent": source_agent,
         "payload": json.dumps(payload), "trace_id": trace_id},
        maxlen=10_000, approximate=True,  # 近似裁剪，避免联调期间Stream无限增长占用Redis内存
    )

async def consume(event_type: str, group_name: str, consumer_name: str, handler) -> None:
    """常驻后台监听循环，FastAPI启动时为每个需要消费该事件的Agent起一个后台任务调用本函数。"""
    stream_key = f"stream:{event_type}"
    try:
        redis_client.xgroup_create(stream_key, group_name, id="0", mkstream=True)
    except ResponseError as e:
        if "BUSYGROUP" not in str(e):
            raise

    # 重启后先重放自己的Pending Entries List（未ACK消息），再转入正常监听——重启补偿靠这一步
    read_id = "0"
    while True:
        entries = redis_client.xreadgroup(group_name, consumer_name, {stream_key: read_id},
                                           count=10, block=0 if read_id == ">" else None)
        for _, messages in entries:
            for msg_id, fields in messages:
                if not handler.already_processed(fields["trace_id"]):  # 幂等：at-least-once投递可能重复
                    handler(fields)
                redis_client.xack(stream_key, group_name, msg_id)
        if not entries:
            read_id = ">"  # PEL重放完毕（本轮无数据），切换为阻塞监听新消息
```

- **常驻监听而非轮询一次**：`consume()`在FastAPI `lifespan`/`on_event("startup")`里为每个Agent起一个后台任务，`block=0`表示无限阻塞直到有新消息，消息一到就能处理，比固定间隔轮询延迟更低、也不空转浪费CPU。
- **幂等性**：Streams是"至少一次"投递，消费者处理完但在`XACK`前崩溃重启会重放同一条消息。`handler.already_processed(trace_id)`用`trace_id`做幂等键判断（或直接给`fin_risk_alert.trace_id`加唯一索引，插入冲突时忽略），避免同一笔预警被重复写入两次。
- **`XACK`失败不影响正确性**：即使`already_processed`跳过了业务处理，仍然要执行`XACK`，避免同一条已处理消息反复出现在PEL里。

**可靠性说明**：消费者处理完必须显式`XACK`；未ACK的消息留在Pending Entries List，消费者重启后用`id="0"`读一次即可补上，不需要额外的MySQL补偿表和定时扫描任务。

### 2.4.1 客户-员工转介机制（Mock真实电话/线下联系）

**背景**：2.2节已明确客户只直接对话客服Agent，投顾助手/业务操作Agent均由理财顾问/客户经理代客户操作。真实业务里这一步靠客户"打电话/去网点找理财顾问"完成，但项目范围明确排除真实IM/电话对接（1.3节Out of Scope），需要一个系统内的轻量方案模拟这次"接上员工"的动作。

**方案：复用`biz_work_order`通用工单表与`work_order_tool`工具外壳，不新建平行机制**——这与F4.1风控监测Agent命中规则后写`biz_work_order`供风控专员处置是完全相同的模式（"Agent自动写工单→员工工作台领取处置"），因此不算新增架构，只是多一种`order_type`取值：

1. **触发**：客户在客服Agent对话中表达购买/赎回/转账意向，或客服Agent检索置信度Score<0.7触发兜底转人工（F1.3已有此意图分类）→ 客服Agent调用`work_order_tool`写入一条`biz_work_order`：`order_type="客户转介"`、`customer_id`、`intent_summary`（LLM从对话中摘要出的意向，如"申购XX产品，意向金额约10万"）、`status="待处理"`。这一步用一条数据库记录代替客户真实拨打电话/到网点这个动作。
2. **领取**：理财顾问、客户经理登录后的工作台查询`biz_work_order WHERE order_type='客户转介' AND status='待处理'`，展示为"待办转介列表"（客户名+意向摘要+提交时间）。**不做"专属客户经理"精准分配**——素材中没有客户与员工的固定归属关系数据，公开待办池是唯一站得住脚的实现方式，任一符合角色的员工均可领取（领取后`status`置为"处理中"，可选记录`handled_by`）。
3. **处理**：员工领取后，基于工单里的`customer_id`用自然语言指令投顾助手Agent（"帮客户A推荐一款XX类型产品"）或业务操作Agent（"帮客户A申购10万XX产品"）代客户执行，即3.2节Gate1~5的正常执行路径。处理完成后把该工单`status`置为"已完成"，工单本身不再承载交易细节（交易细节写入`fin_transaction`，工单只做"意向已被接单/处理完毕"的追踪）。

**与F3.4"工单创建"意图的区别**：F3.4里`workorder:create`权限对应的是客户经理**主动手工创建**的工单（如客户投诉、非标准请求登记），是员工发起的动作；"客户转介"工单是客服Agent在识别到转人工意图时**系统自动创建**，不占用、不依赖`workorder:create`权限（这是AI系统的写入动作，不是人工操作，不需要走RBAC人工权限校验）。两者共用同一张表、同一套状态机，`order_type`字段是唯一区分点。

**Demo串联价值**：客户账号在客服Agent里聊出购买意向（生成工单）→ 切换理财顾问账号登录 → 工作台看到该工单 → 自然语言执行申购（走完整的准入/适当性/熔断/双录/二次确认校验）→ 工单关闭 → 切回客户账号，持仓记录可见新持仓——完整串联5个Agent与RBAC，全程不依赖任何真实电话/IM系统。

### 3.2 员工角色

**角色定义来源**：`CONTEXT.md`领域词典（团队自己维护的统一术语文档）已明确定义"员工：代表公司办理业务的内部用户，具有理财顾问、客户经理、风控专员或管理员等角色"——这4个角色名称是团队产出物内部本来就有的权威定义，不是本次新增，以下表格是对这4个角色在本系统中具体职责的展开，与《功能设计文档》5大Agent的服务对象描述互相印证一致：

| 角色 | 对应Agent服务对象 | 核心职责 |
|---|---|---|
| 理财顾问 | 投顾助手Agent（产品推荐）+ 业务操作Agent（申购/赎回执行） | 产品推荐、风评重做、代客户执行申购/赎回；进一步按销售权限分级（见下） |

| 管理员 | 数据分析Agent"内部员工"+跨Agent风控复核裁决需要 | 风控规则人工复核裁决（`risk:override`）、跨角色数据查看 |

> 理财顾问是唯一同时使用两个Agent的角色：先用投顾助手Agent做只读的产品推荐，客户（线下/电话）确认购买意向后，再切到业务操作Agent执行实际的申购/赎回写操作——这是"推荐"与"执行"两个顺序发生、职责不重叠的步骤，不能合并成一个Agent的职责（见2.2节回调）。

> 命名冲突说明：脚手架自带RBAC体系中已经存在偏运维含义的"系统管理员"概念（对应`Permission.SYSTEM_CONFIG`等8个通用管理权限，管用户/角色/系统配置）。为避免和脚手架自带的系统管理员混淆，本系统在代码/数据里把该业务角色实现为`employee_role="业务管理员"`，与`CONTEXT.md`词典里"管理员"一词指向同一角色，只是落地时加"业务"二字做区分；两者可以是同一个人，但权限集合不同（业务管理员管风控裁决，系统管理员管账号配置）。

**角色互斥关系**：4个角色**非互斥**，一个员工可以同时拥有多个角色（脚手架`UserRoleModel`本身就是多对多关联表，`replace_roles`支持一用户挂多角色）。这一点对4天工期很重要：测试/演示时可以只建2-3个员工账号、每个账号身兼多角色，覆盖全部权限测试用例，不需要为每个角色单独建账号。

**理财顾问的销售权限分级（新发现，原文有明确依据，需补进角色设计）**：《理财产品销售管理办法》第五条给出了一套与`customer_level`（客户AUM分层）完全独立、平行的"员工销售资质分级"体系，按此前梳理遗漏，现补充：

| 销售级别 | 可销售产品风险等级 | 从业要求 |
|---|---|---|
| 初级销售 | R1-R2 | 从业1年以上 |
| 中级销售 | R1-R3 | 从业3年以上，持有相关资格证书 |
| 高级销售 | R1-R5（含私募类） | 从业5年以上，通过公司专项考核 |

系统实现为`employee_role="理财顾问"`账号额外挂一个`advisor_level`字段（初级/中级/高级），业务操作Agent在执行F3.4申购操作前，除了做5.1节的客户风险等级C vs 产品风险等级R匹配，还要额外校验"当前理财顾问的`advisor_level`能否销售这个风险等级的产品"——这是一层此前文档完全没有覆盖的准入校验，属于**员工侧的资质限制**，与"客户侧的适当性匹配"是两回事，两者都要通过才能放行。字段设计见3.4节。

**组织架构澄清（此前版本的错误已订正）**：此前版本曾表述"风控和合规现实中是两个独立部门，团队为了简化合并成风控专员一个角色"——这个说法是错的，已订正。`企业信息.md`显示的组织架构里，本项目虚构公司本来就只设有**一个"风控合规部"**（下辖风险管理、合规审查、稽核审计、信息安全四个团队），并不存在"两个真实部门被团队简化合并"的情况；"风控专员"角色对应的正是这个风控合规部，把"可疑交易上报"纳入风控专员职责范围是与原文组织架构一致的，不是团队的简化处理。

**"基金经理/交易员"不是本系统的用户角色**：这两个岗位负责的是基金公司对募集资金的实际投资运作（选股调仓、下单执行），属于资产管理业务条线；本公司经营的是财富管理代销业务（高频问答对.txt Q11："基金是由基金公司发行和管理的投资产品，通过XX科技等代销渠道销售"），公司本身没有产品/投研/交易/份额登记等自主管理基金的部门，组织架构中也不存在基金经理/交易员岗位。本系统服务的是财富管理/客户服务条线（面向客户的销售、咨询、风控、操作），不模拟基金经理/交易员的行为，详见1.3节Out of Scope的说明。

角色与业务操作Agent的8种意图权限对应关系见4.3节F3.4。

### 3.3 RBAC权限矩阵（基于脚手架扩展）

脚手架 `RoleModel.create_role`/`UserRoleModel.grant_role` 无需结构变动，"理财顾问/风控专员/客户经理/业务管理员"直接作为新增角色记录。需要在 `Permission` 常量类里补充以下业务权限字符串（原有仅8个通用管理型权限，需新增）：

| 权限标识 | 说明 | 拥有角色 |
|---|---|---|
| `product:query` | 产品查询（员工专用） | 理财顾问、客户经理、风控专员 |
| `product:recommend` | 产品推荐 | 理财顾问 |
| `operation:purchase` | 申购操作 | 理财顾问 |
| `operation:redeem` | 赎回操作 | 理财顾问 |
| `operation:transfer` | 转账操作 | 客户经理 |
| `risk:reassess` | 风评重做 | 理财顾问 |
| `customer:info_update` | 客户信息更新 | 客户经理 |
| `risk:suspicious_report` | 可疑交易上报 | 理财顾问、客户经理、风控专员 |
| `workorder:create` | 工单创建 | 客户经理 |
| `risk:override` | 风控规则人工复核/处置 | 风控专员、业务管理员 |
| `data:nl2sql_query` | NL2SQL数据查询 | 全体内部员工 |

`operation:purchase`权限是"能不能操作申购"的开关，是否**放行某一笔具体申购**还要在业务逻辑层叠加两次校验：客户侧的C(风险等级)-R(产品等级)适当性匹配（5.1节），以及员工侧`advisor_level`能否销售该风险等级产品（3.2节）——三者都通过才允许执行，权限矩阵本身不足以表达后两层，需要在F3.4的业务逻辑里实现。

### 3.4 用户表扩展方案

不新建`sys_user`平行表，直接在脚手架 `base_user`（`UserModel`）表基础上扩展字段（`BaseDBModel`的`_ensure_columns_exist()`自动补列）：

- `employee_role`：理财顾问/风控专员/客户经理/业务管理员/NULL（客户无此值）—— **核心字段**，驱动第3.3节RBAC权限矩阵
- `advisor_level`：初级/中级/高级/NULL（仅`employee_role="理财顾问"`时有值）—— **核心字段**，驱动该理财顾问可操作的产品风险等级上限（R1-R2/R1-R3/R1-R5，见3.2节）
- `customer_level`：普通/金卡/白金/钻石/私行/NULL（员工无此值）—— **展示字段**，用于客户人设/demo展示与投顾话术风格，不驱动适当性匹配或权限判断（原因见3.1节）

`user_type`（CUSTOMER/EMPLOYEE）用现有`extra_data JSON`字段承载或作为独立补充列，二选一在开发计划阶段拍板。

## 5. 核心业务规则库

> **本章数据来源说明**：以下规则全部逐条核对自《个人投资者适当性管理指南》（JR-AST-2024-001）、《理财产品销售管理办法》（JR-SPM-2024-003）、《反洗钱可疑交易识别规则》（JR-AML-RULE-2024-001）、《投资者风险画像研判规则》（JR-RULE-2024-001）原文，条款号随内容标注，供开发和答辩时逐条溯源；此前版本中未标注来源、由团队按经验估算的数值，已在第10章逐条列出并说明处理方式。

### 5.1 适当性匹配规则

> **两层准入结构说明**：适当性匹配不是只看风险等级一个维度，实际上分两层——第一层是**产品类型准入**（能不能接触到这类产品），第二层才是**风险等级匹配**（C vs R）。公募基金人人可买，只要满足风险等级匹配；私募基金/专户理财/资管计划等非公开产品，即使风险等级匹配，也必须先通过"合格投资者"资格核验（本节"专业投资者豁免"标准即对应此门槛：金融资产≥500万或近3年年均收入≥50万+2年以上投资经验），且不能由理财顾问通过业务操作Agent一键直接完成，必须配合线下资格认定、风险揭示书签署、双录、冷静期等流程。**因此4.3节F3.4的"申购/赎回"自助操作范围限定为公募基金/标准化产品**，私募类产品的申购在系统里只能走"提交预约/资格初核"，不能直接执行到位。

- **客户风险分级 C1-C5**：16题风评问卷，满分100分，六维度权重——年龄10%/收入状况20%/资产规模20%/投资经验20%/风险承受能力20%/投资目标10%（《适当性管理指南》第七条）；20-35分C1保守型、36-50分C2稳健型、51-65分C3平衡型、66-80分C4进取型、81-100分C5激进型（第十条）
- **产品风险分级 R1-R5**：R1低风险（国债/存款/货币基金/保本理财/大额存单）、R2中低风险（纯债基金/非保本固收理财/债券型资管计划）、R3中风险（混合基金/固收+权益信托/FOF/指数增强）、R4中高风险（股票基金/偏股混合/私募证券投资基金/商品基金/QDII）、R5高风险（期货期权/结构化产品/场外衍生品/加密货币基金）（《适当性管理指南》第十一条）
- **匹配矩阵（硬规则）**：C1只能买R1-R2；C2至R3；C3至R3（R4需签风险揭示书，持仓≤总资产20%）；C4至R4（R5需揭示书，持仓≤总资产10%）；C5全可（第十二条）。硬匹配原则：正向匹配须投资者等级≥产品等级、投资者等级低于产品等级一级以上直接拒绝、C1不得购R3+、C2不得购R4+（第十四条）
- **专业投资者豁免**：金融资产≥500万+近3年年均收入≥50万+2年以上投资经验+通过专业测试，四者同时满足（第五条）；豁免适当性匹配但仍需信息核实和风险告知（第十五条）
- **机构客户特别豁免**：经合规部门审核批准的机构客户，可根据其风险管理能力豁免部分匹配要求（第十五条第4项）
- **拒绝规则（须全部实现，此前版本遗漏后两条）**：①C1/C2超权限购买且不满足豁免条件；②风评过期（超12个月）未重评；③拒填风评问卷；④提供虚假信息经查实；⑤法律法规明确禁止销售的产品；⑥客户被列入公司禁止交易名单（第十六条）
- **特殊人群/年龄相关限制**：已整合进5.3节"硬性熔断规则FM-01"统一维护，避免与本节重复，此处不再复述
- **双录要求（第十七条）**：普通投资者首次买R3+、65岁以上购买非R1产品、豁免方式超权限购买、单笔>50万元、销售复杂结构产品或私募产品，五种情形均需录音录像；录制须在网点内、720P以上、记录身份确认/产品介绍/风险揭示/客户确认/签署全流程，保存期≥20年（第十八~二十条）
- **冷静期（第二十一~二十三条）**：私募基金/信托计划/券商资管/其他私募资管产品均为24小时（自合同签署起算），投连险为15个自然日（自签收保单起算）；期间可无条件全额退款、公司3个工作日内退还本金、不得电话回访干扰撤资决定；私募类产品须在冷静期届满前由**非销售人员**（客服/合规部门）全程录音回访确认，回访中客户仍要求撤资的立即办理
- **复评机制（第二十四~二十六条）**：年度复评（每12个月）；触发式复评（主动要求超权限购买/单笔变动>50万或年度累计>200万/异常交易行为/年满65周岁等重大信息变更/合规部门认定市场重大变化）；到期前30/15/7日分级提醒；到期未评估自动冻结新购权限（仅允许赎回存量）；降级后限制超权限产品追加申购但可持有到期或赎回；升级后开放新购权限

> ⚠️ **产品风险评级方法存在两份原文口径不一致（已决策，见第10章第7项）**：《适当性管理指南》第十三条给出的是"流动性20%+信用风险20%+市场风险25%+结构复杂性20%+杠杆15%"五维度定级法；《理财产品销售管理办法》第七条给出的是另一套"定量60%（历史最大回撤20%+年化波动率15%+流动性评分15%+杠杆水平10%）+ 定性40%（底层资产复杂度15%+发行机构信用15%+信息透明度10%）"评级法——二者维度划分和权重都不同，是两份老师素材本身就存在的口径差异，不是团队转抄出错。**团队决策**：不实现评级引擎，`fin_product.risk_level`按《个人理财产品手册》里各产品条目本身已经直接标明的风险等级（如"XX货币基金｜R1""XX科技创新股票｜R4"）作为静态字段导入即可——手册给的是成品结果而非原始量化指标（回撤/波动率/流动性评分等两份公式都需要的底层数据在业务素材里并不存在），倒推指标去凑已有等级没有意义。两份评级方法仅作为背景知识保留在本节；**若被现场追问"公式选哪个"，统一口径回答《理财产品销售管理办法》第七条**（该条专门针对产品销售定级场景设计，比第十三条更贴题），但明确说明团队未真正实现该算法。

### 5.3 客户画像研判规则

> **重要架构说明——与5.1节风评问卷是两套并行的C1-C5，不是同一件事**：本节的四维度加权模型与5.1节的16题问卷是`CONTEXT.md`词典里"客户画像"与"风险评估"两个不同概念（对应`fin_customer_profile.risk_score`与`fin_risk_assessment.total_score`两个不同字段，见6.1节）——16题问卷是特定日期做一次、有12个月有效期的**风险评估**，用于开户/适当性判定；本节的四维度模型是持续动态更新的**客户画像**，用于个性化推荐/异常监测，且其内部"风险偏好"维度（维度三）直接把问卷百分制得分作为四个输入之一（经换算表转换），并非另起炉灶，两套C1-C5可能得出不同的等级结果，产品匹配等强合规判断以5.1节问卷版为准，投顾推荐等个性化场景用本节画像版。

依据《投资者风险画像研判规则》（JR-RULE-2024-001）：

- **四大特征维度及权重（第四条）**：基础属性25%、投资经验25%、风险偏好30%、行为异常20%
- **综合评分公式（第十条）**：`综合得分 = 维度一×25% + 维度二×25% + 维度三×30% + 维度四×20%`（满分100）
- **分层标准（第十一条）**：0-25分C1(R1-R2)、26-40分C2(R1-R3)、41-60分C3(R1-R4需揭示书)、61-80分C4(R1-R5需揭示书)、81-100分C5(R1-R5)

**维度一 基础属性（满分25分，第五条）**：`（年龄分+学历分+职业分+收入分+资产分）÷5÷10×25`，五项均为0-10分档：年龄分6档（26-35岁最高10分，65岁以上最低3分）；学历分4档（高中4分~硕士以上10分）；职业分8档（公务员/事业单位10分~无固定职业2分）；年收入分6档（<10万3分~>300万10分）；可投资资产分7档（<5万2分~>1000万10分）。

**维度二 投资经验（满分25分，第六条）**：`（投资年限分+产品复杂度分+交易频率分+历史收益分）÷4÷10×25`，四项均为0-10分档：投资年限6档（无经验2分~10年以上10分）；持有产品最高复杂度6档（仅存款2分~期货期权私募结构化10分）；交易频率4档（极低频/低频/中频递增，但周均3次以上"高频"倒扣为6分，识别过度交易）；近三年年化收益6档（无记录3分，<-15%为3分，5%-15%为8分，>15%为9分但需排查是否过度冒险）。

**维度三 风险偏好（满分30分，上限30/下限0，第七条）**：`维度三得分 = 风险测评得分 + 情绪化交易扣分 + 亏损承受调整`。风险测评得分由5.1节问卷百分制换算：20-35→5分/36-50→10分/51-65→15分/66-80→20分/81-100→25分。情绪化交易扣分（AI行为分析识别）：追涨杀跌（净值新高/新低3日内追买/杀跌）-3分、恐慌赎回（大跌>5%当日赎回超持仓50%）-5分、FOMO式加仓（连涨3日后单次加仓超月均3倍）-2分、90天内调仓超3次-3分。亏损承受能力调整：不能承受任何亏损-5、可承受5%以内-2、10%-20%为0基准、20%-40%为+3、40%以上为+5。

**维度四 行为异常（满分20分，修正因子，第八条）**：8种异常行为识别——频繁赎回（30日内≥5次，中）、大额集中交易（单日交易额>总资产50%，中）、非正常时段交易（0-6点频繁登录/交易，低）、突然大额入金（超历史均值5倍，中）、分散转出（单日转出至≥5个不同银行账户，高，触发反洗钱预警）、产品风险越级（要求购买超风险等级2级以上，高，拒绝并重新评估）、信息频繁变更（30日内变更手机/地址≥3次，中）、代理操作（频繁非本人设备/IP，高）。计分：无异常20分、1-2项低风险15分、1-2项中风险10分、3项以上中风险5分、任何高风险异常0分。

**硬性熔断规则 FM-01~05（第九条，一旦满足即强制限制，不允许人工绕过，此前版本仅覆盖年龄一项，现全部补齐）**：

| 规则 | 触发条件 | 处理 |
|---|---|---|
| FM-01年龄限制 | <18岁 | 禁止开户 |
| | 18-22岁 | 可开户，购R4+需监护人知情同意书 |
| | >70岁 | 购R3+需到网点当面签署风险确认书 |
| | >80岁 | 仅允许R1-R2，购R3需特殊审批 |
| FM-02无收入低资产 | 无固定收入且资产<1万元 | 仅允许R1-R2 |
| | 无固定收入且资产1-5万元 | 仅允许R1-R3，且R3持仓≤总资产30% |
| FM-03风评过期 | 超12个月未更新 | 冻结新购（可赎回存量），须重评后解冻 |
| | 超6个月未更新 | 推送重评提醒，不限制交易 |
| FM-04身份信息异常 | 证件过期超90天 | 冻结全部交易权限 |

**特殊场景处理（第十三~十六条）**：多账户冲突取更保守评级（线上线下合并/不同子公司独立评级但共享黑名单）；信息不完整时收入缺失按当地最低工资估算且评级下调一档、资产缺失仅按已知金融资产评估、投资经验缺失给默认3分、联系方式失效限制非柜面交易、多项缺失(>3项)暂停新开户；**客户自评与AI评估不一致**（取AI结果为准，非各打五十大板）——差1档允许申请人工复核，差2档须到网点面对面评估，差3档以上触发合规调查排查误导欺诈；其他特殊场景：精神障碍/认知障碍客户需监护人代理、外籍人士增加国籍风险因子高风险地区下调一档、在校学生收入按0计算仅限R1-R2、失信被执行人限制大额申购、市场极端波动（单日跌幅>7%）全部当日赎回二次确认且暂停新开户风评72小时。

**画像更新机制（第十七~十八条）**：定期更新（风评到期前30天，重评全部四维度）、事件触发（资金变动>50万，重算基础属性维度）、行为触发（交易模式显著变化，重算经验+行为异常维度）、市场触发（指数波动>20%，重算风险偏好维度）、人工触发（客户主动申请，全维度重评）；每月画像漂移检测——交易行为与画像匹配度<60%触发复核、同画像群体收益率偏离>2个标准差检查模型、投诉率超均值2倍检查匹配合理性。

| 信息来源 | 初始置信度 |
|---|---|
| 风评问卷 | 0.90 |
| 交易行为数据 | 0.80 |
| AI从对话中提取 | 0.60 |
| 用户自述 | 0.40 |
| 系统默认值 | 0.20 |

计算公式：`confidence = clamp((base + gain - penalty) × decay, 0, 1)`，其中 `gain = min(evidence_count × 0.05, 0.3)`，`penalty = conflict_count × 0.1`，`decay = max(0, 1 - age_days/365 × 0.2)`。

召回排序另用指数衰减算时效性分：`timeliness = exp(-age_days / 180)`（半年半衰期）。

综合重排（四因子加权，权重为可调超参数）：`综合得分 = 0.4×语义相关性 + 0.3×置信度 + 0.15×时效性 + 0.15×场景权重`。

> ⚠️ 以上来源初始权重、`gain/penalty/decay`系数为记忆架构设计原文给出，可直接使用；但**四因子重排权重(0.4/0.3/0.15/0.15)老师原文未给数值，是团队拟定的示例值**——排序逻辑是"语义相关性必须最高（检索到不相关记忆，置信度再高也没用）＞置信度（决定这条记忆有多可信）＞时效性/场景权重并列最低且相等（次要修正项，无理由认为哪个更重要）"，不是随机拍定，但仍**未经实测数据验证**，依据与调优方式见第10章第2项。

#### 5.4.2 风控置信度（对应F4.1，团队补充设计，解决老师素材留白）

置信度与预警级别(alert_level)是两个独立维度——alert_level由规则命中数+是否历史重复决定严重程度，置信度衡量"这条预警有多大把握不是误报"。**强/中/弱信号的分类不是团队另起的标准，直接复用5.2节20条规则自带的、来自《反洗钱可疑交易识别规则》原文的🔴🟠🟡🔵风险等级**：

| 信号强度 | 权重 | 对应风险等级 | 规则编号 |
|---|---|---|---|
| 强信号 | 0.35 | 🔴高 | RW-004、RW-005、RW-011、RW-013、RW-018、RW-019 |
| 中信号 | 0.20 | 🟠中高 | RW-002、RW-003、RW-006、RW-009、RW-010、RW-014、RW-016、RW-017、RW-020 |
| 弱信号 | 0.10 | 🟡中 / 🔵低 | RW-001、RW-007、RW-008、RW-012、RW-015 |

> ⚠️ 分类标准（哪些规则算强/中/弱）已挂钩5.2节权威的风险等级，**但0.35/0.20/0.10/0.15这四个具体权重数字本身仍是团队拟定的示例值**，非权威依据，依据与调优方式见第10章第1项。

```python
RULE_WEIGHT = {
    "RW-004": 0.35, "RW-005": 0.35, "RW-011": 0.35, "RW-013": 0.35, "RW-018": 0.35, "RW-019": 0.35,
    "RW-002": 0.20, "RW-003": 0.20, "RW-006": 0.20, "RW-009": 0.20, "RW-010": 0.20,
    "RW-014": 0.20, "RW-016": 0.20, "RW-017": 0.20, "RW-020": 0.20,
    "RW-001": 0.10, "RW-007": 0.10, "RW-008": 0.10, "RW-012": 0.10, "RW-015": 0.10,
}

def calc_risk_confidence(triggered_rules, is_repeat) -> float:
    weight_sum = sum(RULE_WEIGHT[r.rule_id] for r in triggered_rules)
    repeat_bonus = 0.15 if is_repeat else 0.0
    return round(min(1.0, weight_sum + repeat_bonus), 2)
```

映射标签：`<0.4低`，`0.4~0.7中`，`>0.7高`。
