# 财富管家模拟真实数据要求

本文档定义数据库重建时的模拟数据标准。目标是模拟一个真实财富管理公司的客户生命周期，而不是生成一批只有编号、随机金额和孤儿关联的测试行。

## 总体规则

- 客户可以使用化名，但展示姓名必须是自然中文姓名；`wb_seed_customer_001` 等只能作为内部账号或稳定自然键，不能作为 `customer_name`、对话称呼或页面标题。
- 每条客户业务记录必须能通过 `customer_id` 回查到 `base_user`，每条产品业务记录必须能通过 `product_id` 回查到 `fin_product`。
- 金额、持仓、份额、净值、手续费、收益和交易状态必须相互可计算，禁止只填一个总额再随机填其它字段。
- 交易、持仓、风评、预警、工单和会话要形成时间顺序，体现“开户/测评 → 了解产品 → 申购 → 持仓 → 收益/预警 → 赎回或追加”的生命周期。
- 所有日期使用相对当前日期的业务时间，不能全部使用同一天；至少覆盖近 12 个月，并包含今日/近 7 天活动数据。
- 任何客户级数据不得使用真实身份证号、银行卡号、手机号或签名；可使用格式正确但不可投产的脱敏值。
- 产品表、FAQ、问答、知识库和向量切片属于知识/产品基础数据，不得因为重建客户数据而删除或覆盖。

## 一、MySQL 业务库

### `base_user`

建议客户 180 人，风险等级分布约为 C1 20%、C2 23%、C3 27%、C4 20%、C5 10%。

- 客户：`user_type=CUSTOMER`、`source_module=fin`、状态以 active 为主，少量 inactive 体现销户/冻结。
- 展示资料：化名、出生年份、职业、城市、客户等级、资产规模、负责顾问账号写入 `extra_data`。
- 账号、邮箱必须稳定且唯一；账号可编码，但页面始终使用 `display_name`。
- 员工：理财顾问、客户经理、风控专员、业务管理员，建议 30 人；员工账号不能混入客户统计。

### `base_role` / `base_user_role`

- 为客户、理财顾问、客户经理、风控专员、业务管理员分配正确角色。
- 普通理财顾问只能管理 `fin_customer_profile.advisor_id` 指向自己的客户或自己领取的工单客户。
- 业务管理员/最高权限角色才能查看全量客户。
- 客户不能获得员工操作权限；授权记录保留 `granted_by` 和 `source_module`。

### `fin_product`

这是产品基础表，必须保留已有数据；如需补充，只能幂等增加真实业务风格产品。

- 建议至少覆盖 R1-R5，每个风险等级 8-15 个产品。
- 字段必须包括产品代码、产品名称、类型、风险等级、起购金额、当前净值、净值日期、管理人、状态。
- 产品名称使用“稳享纯债”“均衡配置”等自然名称，不使用“R3演示产品”。
- 产品代码可以是内部编码，但产品名称、类型和风险说明必须可读。

### `fin_product_nav_history`

- 每个在售产品至少 30-180 个历史净值点，按交易日递增。
- 净值变化应平滑并符合产品风险：R1 波动最小，R5 波动最大；禁止每日完全相同或随机跳变。
- 当前净值必须等于最新一条历史净值，净值日期不能晚于当前日期。

### `fin_customer_profile`

每个有效客户一行，且必须有 `advisor_id`。

- 保存风险等级、风险分数、四维评分、资产配置、产品偏好、记忆单元和画像更新时间。
- `asset_allocation` 各类别占比合计 100%，并与持仓产品大类大致一致。
- C1/C2 客户不应出现全部高风险资产；C4/C5 可有权益、私募或较高波动产品。
- 未完成测评的客户 `risk_level` 可为空，不能伪造 C1。

### `fin_risk_assessment`

- 已有客户建议 85%-95% 有有效测评，少量客户未测评或已过期，用于验证强制测评流程。
- 每份记录必须有 16 题答案、总分、C1-C5 等级、评估时间和 12 个月有效期。
- 等级必须由正式规则服务计算，答案与总分/等级一致，不能由 LLM 自由编造。
- 同一客户允许有历史测评，但只有最新且 `valid_until > NOW()` 的记录可用于适当性判断。

### `fin_holdings`

- 每个已投资客户 1-6 条持仓，未投资客户可以为空。
- `shares * purchase_nav` 应接近成本金额，`current_value` 由当前净值计算，盈亏和收益率由成本与市值计算。
- 持仓产品风险等级不得长期明显高于客户有效测评等级；违规场景应通过失败交易或预警表达。
- 购买日期必须早于当前日期，且能在交易表找到对应申购成交记录。

### `fin_transaction`

建议每个活跃客户 2-12 条交易，覆盖申购、赎回、转账、分红等实际业务。

- 成交申购：必须有产品、金额、份额、净值、手续费、渠道、成交时间和唯一幂等键。
- 赎回：金额/份额不能超过客户当时持仓；成交后持仓应减少。
- 失败交易：保留失败原因，例如未完成风评、风险等级不适配、余额不足，但不能增加持仓。
- 转账交易可无产品，但必须有合规审查关联和可疑场景说明。
- 时间顺序应支持“先测评、后交易；先申购、后持仓；先交易、后预警”。

### `fin_risk_alert`

- 预警必须由真实规则场景产生，并关联客户和相关交易 ID。
- 建议覆盖夜间大额转账、短期频繁交易、风险等级不适配、异常地区等场景。
- 每条预警包含级别、规则编号、触发详情、状态、处理人、处理备注和处理时间。
- 已处理预警应有闭环记录；待处理预警应能生成对应工单。

### `biz_work_order`

- 工单必须有客户 ID、客户化名、业务类型、来源、标题、意向摘要、优先级、状态和创建时间。
- 风险等级、产品风险说明、收益查询等知识性问题应由客服 Agent 直接回答，不应无故创建工单。
- 申购、赎回、转账审核、账户变更、投诉、风险预警等需要人工或后台动作的事项才创建工单。
- 工单应按角色分流：申购/赎回归理财顾问，转账归客户经理/运营，风险预警归风控专员。
- 普通员工只能领取自己业务范围的待办；领取后应进入对应 Agent 服务该客户。
- `customer_id IS NULL` 的旧孤儿工单不得猜测客户，只能隔离、标记或人工补录。

### `conversation_archive` / `base_llm_session` / `base_llm_conversation`

- 每个客户可有客服、投顾、运营等不同会话；会话中的姓名、产品、金额必须来自该客户真实模拟数据。
- 会话时间要与工单/交易关联，支持“客服回答 → 转人工 → 顾问回执 → 客户收到通知”的链路。
- 归档记录必须有消息数量、摘要、情绪、是否解决、是否转人工和归档原因。
- 不要把公司知识问答误写成客户个人记忆。

### `biz_operation_audit`

- 记录关键操作：申购、赎回、转账、风评提交、工单领取、风险处理、权限变更。
- 每条记录必须有事件 ID、trace ID、操作员工、客户、意图、结果和时间。
- 审计数据只追加，不使用随机覆盖；失败操作也要保留失败原因。

### `biz_compliance_evidence`

- 只存脱敏的合规证据索引：客户、产品、证据类型、对象 URI、哈希、签发/复核事件。
- 不存真实签名、证件或银行卡原文；文件对象放 MinIO，MySQL 保存索引和 SHA-256。

### `fin_verified_payee`

- 仅保存账户 HMAC、末四位、收款人名称 HMAC、验证状态、验证人和时间。
- 不保存完整银行卡号或身份证号；验证收款人必须属于明确客户。

### `fin_knowledge_meta`、FAQ、产品问答

这些是知识数据，不属于客户业务数据重建范围。已有记录、文档切片和问答对必须保留。

- 只允许通过审核后的产品说明、费率、风险揭示、制度文件增量更新。
- 不要用客户姓名、交易记录或随机文本生成知识切片。
- 不要执行清空集合、删除 FAQ 或重建全部向量的脚本。

## 二、Redis

Redis 数据应使用隔离前缀，禁止 `FLUSHDB`、`FLUSHALL` 或按模糊通配符删除生产键。

- 客户会话：`session:{customer_id}:messages`，保存近期客服/投顾消息，设置 TTL。
- 客户画像缓存：`profile:{customer_id}`，内容必须与 MySQL 画像一致，失效后可重建。
- 客户回执通知：`notifications:user:{customer_id}`，记录工单结果、来源 Agent、摘要和时间。
- 跨 Agent Stream：`stream:work_order`、`stream:work_order_result`、`stream:risk_alert`，消息必须有 customer_id、trace_id、source_agent 和幂等键。
- 演示数据使用 `wb-seed:20260817:*` 隔离前缀；会话和缓存设置有限 TTL，Stream 不得重复写入同一稳定事件。

## 三、Milvus / 向量库

向量库属于知识检索和客户长期记忆两类数据，必须分开管理。

### 产品/FAQ/制度集合

- 来源是产品说明书、风险揭示书、费率表、公司制度、FAQ 和审核问答。
- 每个切片必须有来源文件、页码/段落、产品代码或文档 ID、版本、审核状态和更新时间。
- 只能增量写入或按文档版本替换；不得因客户数据清理删除这些集合。

### 客户长期记忆集合

- 只写入明确授权、脱敏、与客户相关的稳定事实，例如投资偏好、服务偏好和已确认目标。
- metadata 必须包含 customer_id、session_id、memory_type、created_at、source 和 confidence。
- 不写入完整身份证号、银行卡号、密码或未确认的 LLM 猜测。

## 四、Neo4j

- 客户节点、产品节点、顾问节点和关系必须能回查 MySQL 自然键。
- 关系示例：客户 `HELD` 产品、客户 `ADVISED_BY` 顾问、客户 `TRADED` 产品、客户 `ASKED_ABOUT` 产品。
- 每条关系带时间、金额/份额（适用时）、来源事件 ID 和数据版本。
- 不要创建只有编码没有名称的孤立节点；客户节点至少有化名和内部 ID。

## 五、MinIO

- 仅保存脱敏演示证据、产品文档或审核附件，路径使用 namespace 和稳定业务键。
- 对象 metadata 包含来源、版本、seed namespace、SHA-256 和证据类型。
- 不上传真实证件、银行卡、签名原件或客户隐私文件。
- 删除客户模拟数据时，只删除明确属于该客户 namespace 的对象；产品文档和知识源文件保留。

## 最低验收标准

1. 随机抽取 10 个客户，均能从账号 → 画像 → 风评 → 持仓/交易 → 工单/会话完整回查。
2. 随机抽取 10 条成交交易，金额、份额、净值和持仓变化可复算。
3. 所有客户展示字段都是中文化名，不出现客户编号、内部账号或 `客户+数字`。
4. 产品、FAQ、问答和向量知识集合清理前后数量不减少。
5. 普通顾问、风控、客户经理和管理员看到的数据范围符合角色职责。
6. 未完成风评客户能被识别并引导测评，不能被默认分配风险等级。
