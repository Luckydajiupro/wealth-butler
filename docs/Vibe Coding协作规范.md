# Vibe Coding协作规范

## 0. 文档说明

《开发计划.md》回答"谁在哪天做什么功能"，本文档回答"每个人打开AI编码agent（vibe coding工具）后，具体怎么提需求、怎么测、怎么把代码合到一起"。背景是4天工期下全员用AI编码agent写代码、且团队多数人不熟悉git操作，需要一套统一、低门槛的规范，既避免各自为战导致代码拼不到一起，也为答辩必问题"Vibe Coding经验与踩坑"积累真实素材。

**产出形式说明**：本文档目前是书面规范，团队每人对着执行；代码仓库建好后（见开发计划Day1第一项前置任务），会把其中适合自动化的部分（测试用例生成、合并前自检）转成Claude Code的Skills，届时在§6补充落地方式，不影响现在直接按本文档开工。

## 1. AI编码agent工作流程

- **开工前先喂上下文**：让AI读取相关设计文档再动手——写业务表就给它看《表设计文档.md》对应表的字段定义，写接口就给它看《API接口设计文档.md》对应契约，写Agent就给它看《Agent设计文档.md》对应System Prompt骨架。不要让AI凭空猜字段/猜接口路径，这是vibe coding返工率高低的关键差异。
- **任务粒度要小**：一次只让AI做一件具体的事（例如"实现RW-001规则判定逻辑"），不要一次性丢"把风控Agent写完"这种大任务。粒度小才方便review、方便commit、方便出问题时定位是哪一步引入的。
- **必须人工过一遍、不能盲目接受的场景**：
  - 涉及金额、权限校验、风控规则阈值判定的代码——错了直接影响答辩演示的核心指标
  - SQL/Cypher拼接相关代码——《脚手架复用能力盘点.md》已指出脚手架自带的`SQLBuilder`不做表名/字段白名单，AI很可能照抄这种不安全模式，必须人工确认白名单校验逻辑真的写了、真的生效
  - 跨文件改动（比如改了Model字段但AI没同步改调用处）
- **可以直接接受、不用细看的场景**：样板代码（CRUD骨架、Pydantic字段定义、日志打印语句）
- **踩坑记录随手攒**：每人在当天会议纪要里顺手记一笔"AI生成了什么错误代码→怎么发现的→怎么改的"，不要留到Day4现场回忆——这是答辩必问题的素材来源。

### 1.1 Codex 写代码、Claude Code 做 review

团队采用"Codex 写、Claude Code 审"的双工具流水线，两者职责分离、不要混用：

- **Codex 负责写代码**：拿到明确的设计文档、文件落点、参照文件后，一次性生成实现（单文件或多文件三件套）。优势是一次性交付完整代码，适合"规格已经想清楚、就差动手写"的活。
- **Claude Code 负责 review**：审查合并进主分支的代码是否符合同一套编码规范、测试要求、安全底线，理解多份文档上下文、能交叉核对字段/接口是否对齐。优势是交互式、能读懂设计文档语义，适合"照着规范挑毛病"的活。

**流程时序（写在前、审在后）**：Codex 写代码 → 各人按§5合并到主分支 → **代码合并完成后，Claude Code 统一做 review**。也就是说 Claude 的 review 不是写代码阶段的即时门禁，而是合并后的一次整体质量把关。写代码阶段由写的人按§1自己对关键代码（金额/权限/风控/SQL）人工过一遍，Claude 的统一 review 是第二道、团队层面的把关，两者层次不同、不互相替代。

**给 Codex 的提示词必须一次给足上下文**（Codex 不像 Claude Code 那样多轮对话澄清，漏了关键信息它不会问，会直接猜）。每个 Codex 任务提示词至少带齐四样：

1. **设计规格来源**：引用具体文档段落或路径，例如"按《表设计文档.md》§2.3 `fin_transaction` 表的字段定义实现"
2. **脚手架参照文件**：指明可抄的现成写法，例如"Model 层参照 `Repository/models/` 下已有表的写法，不要自创写法"
3. **文件落点**：对照《架构设计文档.md》§2.1"代码目录落点"，明确新文件放哪一层哪个目录
4. **命名与规范**：提醒它遵守§2（小驼峰命名、不引入新框架）

**示例提示词骨架**：

> 按《表设计文档.md》§2.3 的 `fin_transaction` 表字段定义，在 `Repository/models/` 新建 `finTransactionModel.py`，Model 写法参照现有 `userModel.py`；同时在 `Service/` 新建 `transactionService.py` 实现转账业务逻辑，文件命名遵守小驼峰。不要引入脚手架没有的 ORM 或框架。

**Claude Code 统一 review 的重点**（覆盖§1列出的关键场景）：金额、权限校验、风控规则阈值、SQL/Cypher 拼接这四类代码必须逐行确认，尤其 SQL 拼接要确认白名单校验真的写了、真的生效。Codex 最容易犯的错是"照抄脚手架里不安全或不规范的模式"（例如照抄不做表名/字段白名单的 `SQLBuilder`），这恰恰是 review 最该拦下来的地方。统一 review 的通过判定标准：字段/接口路径与设计文档对齐、命名符合§2、关键路径有对应测试（§3/§4）、无硬编码密钥、各人只改了自己负责的文件（对照《开发计划.md》§1 分工表，防止合并时有人越界改动了别人的模块）。

**防冲突铁律**：同一文件在同一时段只能被一个工具改。统一 review 是合并后对主分支代码的集中检查，此时应暂停新代码写入（或改完合并后再审一次），避免"边审边有人往主分支推新代码"导致 review 结果失真；按《开发计划.md》§1 的分工，每个人手上的文件就是自己的"领地"，工具只是帮手，换工具不等于换领地。Codex 生成的代码同样遵守§3测试要求（谁写逻辑谁补对应测试），可以顺带让 Codex 一起生成 pytest 用例草稿，再由 Claude Code 统一 review 时按§4核对完整性。

## 2. 编码规范

- **复用优先**（ADR-1原则的编码级延伸）：新写代码前先看脚手架里有没有类似模式可抄（新业务表Model参照`Models/userModel.py`，新Agent参照`Ai/agents/nl2cypherAgent.py`/`Ai/base/baseAgent.py`），不要放任AI重新发明一套写法。
- **文件命名跟随脚手架现有约定**：脚手架文件名是小驼峰风格（如`riskEngineService.py`），AI默认经常输出下划线命名（`risk_engine_service.py`），生成后要检查并按项目风格改。新文件具体放哪一层、哪个目录，对照《架构设计文档.md》§2.1"代码目录落点"。
- **禁止事项**：不引入脚手架没有的新框架/新ORM（违反"单体不过度设计"原则）；不把测试数据/写死的if分支混进正式业务逻辑；不把API Key、数据库密码等硬编码进代码（见§5"忽略文件"）。

## 3. 测试要求

- **测试框架**：沿用脚手架现有约定用pytest（`Repository/test/`、`Ai/base/test_*.py`已经是这个风格），新代码比照现有test文件的写法，不引入新测试框架。
- **必须覆盖的范围（按优先级，4天工期不追求覆盖率数字，追求"关键路径不翻车"）**：
  1. 《开发计划.md》标🔑的7项关键路径任务，每项至少有一个能跑通的最小验证用例
  2. 20条风控规则——每条至少1个"应该命中"+1个"不应该命中"的边界case，参照需求文档§9.1验收标准（10测试交易以上）
  3. NL2SQL安全校验层——必须有"尝试注入危险SQL被正确拦截"的用例，这是安全底线，不能只测正常查询能跑通
  4. 二次确认状态机（"待确认→已确认→执行"）——`confirm`和`cancel`两条路径都要覆盖
- **谁写测试**：谁写业务逻辑谁写对应测试，不设专职测试人员（4天工期没有这个人力）。李清华Day4上午的端到端联调本身就是一轮系统级测试，不需要重复造轮子。

## 4. 测试用例生成

- 用AI编码agent生成测试用例草稿是被鼓励的做法（比手写快），但生成后要对照下面两个来源核对完整性，不能全信AI自己想的case：
  - **风控规则类**：对照《研判规则提取与落地方案.md》和项目根目录《用户研判规则》原始规则文本，确认边界值覆盖到了（比如">1万"是否包含1万整这种细节）
  - **接口类**：对照《API接口设计文档.md》的请求/响应契约，确认异常路径（401/403/参数校验失败）有覆盖，不是只测happy path
- **测试数据**：优先复用项目已有《用户测试数据》里的客户A/B两个样本；但《开发计划.md》Day3任务已提醒"不能只用A/B两个真实样本"，边界case需要团队自己额外构造。

## 5. 代码合并（Git协作方式）

已与团队确认，考虑到团队多数人不熟悉git操作，采用最低操作门槛的方案：

- **仓库**：GitHub私有仓库，李清华创建并将其余5人加为协作者（Settings → Collaborators）。
- **分支策略**：单一`main`分支，不开feature分支——分支的checkout/merge/rebase是新手最容易出错的环节，直接省掉。配合《开发计划.md》已经按文件/模块把工作分到人（各自Agent文件、李清华独占Repository/EventBus/建表），天然冲突面很小。
- **工具**：推荐用VS Code自带的Git面板（图形化pull/commit/push），不用命令行，出错率低、冲突提示直观。
- **认证**：HTTPS + GitHub个人访问令牌（Personal Access Token），不用SSH key（新手在Windows上配置SSH key容易踩坑）。首次克隆时输一次账号+粘贴token，GUI工具会记住凭证。
- **铁律**：改动前先pull一次，push前再pull一次；只改自己负责的文件（对照《开发计划.md》§1分工表），不要顺手改别人的文件。
- **冲突应急预案**：一旦push被拒绝、提示冲突，不要自己瞎点"合并"，截图现象直接找李清华处理，避免新手用错误方式解决冲突导致代码丢失。
- **备份**：李清华每天收工后在GitHub上打一个tag（如`day1-checkpoint`），作为当天回滚点，不需要其他人操作。
- **忽略文件**：仓库根目录配`.gitignore`，排除`__pycache__/`、虚拟环境目录、`.env`（API Key等密钥文件改用`.env.example`模板提交，真实`.env`不入库）。

## 6. 已落地的Skills清单

团队通用AI编码规范已转成可执行的Skills，落在项目根目录`.claude/skills/`（代码仓库建好后随代码库一并维护）：

| Skill | 内容 | 对应本文档章节 |
|---|---|---|
| `coding-standards` | 编码规范：复用优先、文件落点、小驼峰命名、禁止事项、高风险代码核查 | §2 |
| `comment-standards` | 注释规范：面向刚接触大模型开发的新手读者，WHAT+WHY 都写，大模型概念/脚手架改造/踩坑点必须注释 | （注释补充项） |
| `testing-standards` | 测试规范：pytest、覆盖优先级、谁写逻辑谁写测试 | §3 |
| `test-case-generation` | 测试用例生成：生成后对照两个来源核对完整性 | §4 |
| `merge-standards` | 合并规范：单main分支、GUI工具、push前pull铁律、冲突处理、.gitignore | §5 |
| `code-review` | 代码review规范：合并后统一review的时机、重点、通过判定标准、跨文档一致性 | §1.1 |
| `prompt-engineering` | 提示词工程：5个Agent的System Prompt/意图分类/Tool schema描述/NL2SQL、NL2Cypher生成提示词怎么写 | （提示词领域深化项） |
| `scaffold-reuse` | 脚手架复用：写新代码前查脚手架有什么能复用、哪些必须新写、三个照抄必翻车的警告 | （对应§2"复用优先"的展开） |
| `doc-consistency` | 跨文档一致性：改字段/接口/规则/权限/事件格式时，连带检查受影响文档，避免口径矛盾 | （新增，面向14+份文档的联动维护） |
| `doc-versioning` | 文档版本与变更管理：每份文档维护版本号、变更记录追加（含变更人实名）、联动文档同步升号 | （新增，配合doc-consistency） |

各Skill正文为工具无关的通用规范，Codex 写代码与 Claude Code 做 review 均可引用；如需调整以各Skill文件为准，并同步更新本文档对应章节。
