## 疑点1：风控预警的置信度公式未落地

**现状**：《功能设计文档》只给出定性描述"单规则=低置信、多规则=中置信、多源交叉验证=高置信"，函数签名 `_calc_risk_confidence(triggered_rules, is_repeat)` 没有展开算法。

**关键点先厘清**：置信度（confidence，"这条预警有多大把握不是误报"）和预警级别（alert_level，"这件事有多严重需要多快处理"）是**两个独立维度**，不要混为一谈——这和记忆体系里"置信度≠重要性"是同一个设计原则。alert_level 已经由 `rule_count` + `is_repeat` 决定了（1条→蓝，2-3条或重复→黄，>3条→红），置信度需要单独算。

**建议方案**：给20条规则（RW-001~020）预先标定"信号强度权重"（在规则引擎实现时作为规则元数据的一个字段），例如：

| 权重档位 | 权重值 | 适用规则举例 |
|---|---|---|
| 强信号 | 0.35 | 涉及制裁名单关联、身份异常、拆分交易识别（越难伪装/误报率低） |
| 中信号 | 0.20 | 大额交易、关联账户交易 |
| 弱信号 | 0.10 | 频繁交易、单纯行为模式类规则（容易和正常客户重合） |

计算公式（沿用"加权求和后钳制"的结构，与记忆置信度算法保持同一套代码风格）：

```python
def calc_risk_confidence(triggered_rules: list[Rule], is_repeat: bool) -> float:
    weight_sum = sum(RULE_WEIGHT[r.rule_id] for r in triggered_rules)
    repeat_bonus = 0.15 if is_repeat else 0.0
    confidence = min(1.0, weight_sum + repeat_bonus)
    return round(confidence, 2)
```

映射标签（用于展示"低/中/高置信"）：`<0.4低`，`0.4~0.7中`，`>0.7高`。

**需要评审拍板的点**：20条规则各自归到哪个权重档位——建议直接在规则引擎实现时，由写反洗钱规则那位同学参考《反洗钱可疑交易识别规则.md》里每条规则自带的风险等级(🔴🟠🟡🔵)做映射（🔴→强信号、🟠→中信号、🟡🔵→弱信号），不用另起一套标准。

## 疑点2：记忆体系三个组件细节留白

《记忆架构设计》定位是教学指南，`MemoryUnitValidator`、`MemoryStore`、`recall_memories()` 综合重排公式都只给了调用占位。分三块给建议：

### 2a. MemoryUnitValidator 六维校验（校验的六个维度已在文档流程图里点名，只是没展开规则）

| 校验维度 | 具体规则建议 |
|---|---|
| 枚举值 | `tag` 必须落在预定义标签枚举表内（如 risk_preference/income_level/investment_experience/product_interest…）；`info_type` 必须是 fact/opinion |
| 数值范围 | `confidence ∈ [0,1]`；`evidence_count/conflict_count/recall_count ≥ 0` |
| 时间逻辑 | `create_time ≤ update_time ≤ 当前时间`；若设置了 `valid_until`，需 `> create_time` |
| 来源合法性 | `source` 必须在 `SOURCE_INITIAL` 白名单内（风评问卷/行为推断/AI对话提取/用户自述/系统默认），非法来源一律按"系统默认"兜底且打日志告警 |
| 标签唯一性 | 同一 `customer_id + tag` 不应重复创建新记录，应该走 `deduplicate_and_merge` 合并逻辑（这个方法记忆架构设计里已经有） |
| 内容格式 | `content` 非空、长度 ≤ 500 字符（避免把整段对话原文塞进去，记忆应该是提炼后的短结论） |

校验失败的处理：不要直接丢弃，写入错误日志（流程图里已经这么设计了），方便后续排查是不是LLM抽取阶段出的问题。

```python
    def search(self, customer_id, scenario, query, top_k) -> list[MemoryUnit]:
        # 中期: MySQL按customer_id+tag精确/模糊查询
        # 长期: Milvus向量检索(query做embedding) + Neo4j图谱关联(如适用)
        ...
    def archive(self, unit_id: str) -> None:
        # status改为archived，从热路径(Redis缓存)移除，仅保留MySQL归档记录
        ...
```

**建议不做**独立的归档库/冷存储表，直接复用 `fin_customer_profile` 或新增一张 `fin_memory_unit` 表 + `status` 字段区分，避免多建一套存储增加联调成本（4天工期，能少建表就少建）。

### 2c. recall_memories() 综合重排公式

建议加权求和（四因子，权重可调超参数，需要在配置文件里显式声明，方便调参和写进文档"设计原因"）：

```python
综合得分 = 0.4 × 语义相关性(向量cosine) + 0.3 × 置信度(confidence)
         + 0.15 × 时效性(calc_timeliness，即已有的指数衰减) + 0.15 × 场景权重
```

场景权重表举例（体现"同一条记忆在不同场景下重要性不同"）：

| 场景(scenario) | 高权重标签 |
|---|---|
| product_recommend（投顾推荐时） | risk_preference, investment_experience, income_level |
| customer_service（客服对话时） | complaint_history, product_interest |
| risk_review（风控研判时） | abnormal_behavior, transaction_pattern |

场景权重可以简化实现为：命中高权重标签 +0.2，否则 +0（不用做成连续函数，够用就行）。

## 疑点3：各Agent意图置信度阈值只有客服Agent给了示例(0.6)

**建议阈值表**（原则：涉及资金操作/错误代价越高，阈值应该越高；容错性越强的场景阈值可以放低）：

| Agent | 建议阈值 | 理由 | 低于阈值时的行为 |
|---|---|---|---|
| 智能客服 | 0.6（文档已定） | 错误路由代价低，最多答非所问 | 走兜底话术/引导转人工 |
| 投顾助手 | 0.65 | 直接影响产品推荐，但不涉及资金变动 | 追问澄清具体需求 |
| 数据分析(NL2SQL) | 0.5 | 所有意图最终都走同一条NL2SQL路径，意图分类只影响Schema筛选范围，分类错误的代价是"多注入几张表的DDL"而非功能错误 | 低于阈值时不拒绝，退化为注入全量Schema兜底 |
| 业务操作(NL2API) | 0.75 | 涉及真实资金操作（申购/赎回/转账），误判代价最高 | 不执行，触发澄清追问，绝不能"猜一个意图就执行" |
| 风控监测 | 不适用 | 风控Agent是双轨被动触发型（8条实时/准实时规则消费交易事件流触发，12条日批/周批规则由APScheduler定时批量扫描触发，两者均与用户自然语言输入无关，见需求文档2.4节），走的是确定性规则匹配（`rule.evaluate()`返回True/False），不存在"意图分类置信度"这个概念，避免团队误把这个机制套到风控Agent上 |

> 注：除智能客服Agent的对话方是客户本人外，投顾助手/数据分析/业务操作Agent的"用户自然语言输入"实际都来自**员工**（理财顾问/内部员工/理财顾问与客户经理），意图分类阈值本质上是在校验员工输入的分类置信度，与需求文档2.2节的Agent服务对象结论一致。

## 疑点4：投顾多因子排序里 graph_signal（占15%权重）计算方法未展开

**建议方案**（围绕"避免推荐加剧客户持仓行业集中度"这一设计初衷，功能设计文档里已经点出了这个目的，只是没给公式）：

```python
def calc_graph_signal(candidate_product, customer_holdings: list, graph_tool) -> float:
    candidate_industry = graph_tool.get_industry(candidate_product)
    held_industries = [graph_tool.get_industry(p) for p in customer_holdings]

    # 该行业在客户现有持仓中的资产占比
    industry_concentration = sum(
        h.market_value for h in customer_holdings if h.industry == candidate_industry
    ) / total_holdings_value(customer_holdings)

    if industry_concentration > 0.3:
        return -0.5   # 该产品所属行业已高度集中，降低推荐优先级
    elif candidate_industry not in held_industries:
        return 0.5    # 全新行业，鼓励分散配置
    else:
        return 0.0    # 中性
```

**评审需要确认**：0.3这个集中度阈值、-0.5/0.5/0.0的取值都是可调超参数，建议先按这个跑通功能，答辩前如果有时间可以用测试客户A/B的持仓数据实际调一下效果再定稿。

## 疑点5：反洗钱规则与适当性管理规则口径交叉，避免重复/冲突判定

**现状**：两份政策文档里都出现了"大额转账""双录触发"相关的阈值描述，口径不完全一致；同时《需求文档》里"转账>5万二次确认"这个数字，在风控Agent反洗钱规则表附注的大额交易报告线（转账单笔≥20万，非某条具体RW-00x规则，见需求文档RW-001~020表后附注）和适当性文档的双录规则里也各自出现，容易导致实现时同一个"5万/20万"数字在三个地方硬编码三份，后续改一个漏改另外两个。

**建议方案**：建一张**统一合规阈值配置表**（可以是代码里的一个 `compliance_thresholds.py` 常量文件，或数据库一张小配置表），所有涉及金额/次数阈值的判断逻辑（业务操作Agent的二次确认、风控Agent的规则引擎、适当性双录触发）都从这一份配置读取，不在各自模块里各写一份数字：

```python
COMPLIANCE_THRESHOLDS = {
    "operation_confirm_purchase": 10_000,      # 业务操作Agent-申购二次确认
    "operation_confirm_transfer": 50_000,      # 业务操作Agent-转账二次确认（=反洗钱关注线）
    "aml_single_cash": 50_000,                 # 反洗钱-现金单笔/当日累计报告线
    "aml_transfer_single": 200_000,            # 反洗钱-转账单笔报告线
    "aml_transfer_daily": 500_000,             # 反洗钱-转账当日累计报告线
    "suitability_double_record_amount": 500_000,  # 适当性-单笔超此金额强制双录
}
```

这样即使后续某个阈值要调整，也只改一处，三个Agent的判断逻辑都能保持一致——这个点如果在答辩时被问到"如何保证风控规则和适当性规则不冲突"，也是一个很好的加分回答。

## 疑点6：业务素材中"XX""20XX"脱敏占位符处理

**建议两层处理**：

1. **数据清洗阶段（导入RAG知识库前）**：写一个简单脚本，在把 `.md`/`.txt` 素材切块入库前，统一把占位符替换成项目内部自洽的具体值（比如把所有"XX科技"统一替换成同一个虚构公司名，"20XX年"替换成具体年份如2024年），保证同一个知识库里的数值/称呼前后一致，不然客服Agent检索到两段"XX理财"和"某理财"可能被当成两个不同产品。

2. **Prompt兜底层**：客服Agent的RAG System Prompt里已经要求"仅基于检索内容回答、不编造"，可以再加一条约束：如果检索片段里仍然残留未替换的占位符（用简单正则识别连续大写字母如`XX`或`20XX`这种模式），在拼接进Prompt前做一次二次替换或标记，避免模型原样把"XX理财"念给用户听，显得像没做数据清洗。

**优先级说明**：这一条不影响核心功能验收，工期紧张时可以放到 Phase 5 联调优化阶段做，不需要 Phase 1 就处理。
