## 1. 项目一句话定位

为 XX 科技（持牌综合财富管理机构）打造一套"智能财富管家系统"：用 5 个垂直 Agent（客服 / 投顾 / 风控 / 数据分析 / 业务操作）+ RAG/GraphRAG/NL2SQL/NL2API 四大 AI 能力 + 三层记忆体系，替代人工客服、人工画像研判、人工风控抽查、人工写 SQL、多系统切换操作，同时不能突破适当性匹配、反洗钱等金融合规红线。老师原始文档按 5 周、5 个 Phase 组织验收标准与评分权重（本文档第2、9节沿用这一分组便于对照），但团队实际采用 vibe coding 方式，**真实开发工期压缩为4天**，并复用现成后端脚手架二次开发，Phase 分组不代表真实排期，详见需求文档1.5节。

## 2. 按 Phase 组织的功能模块清单

### Phase 1（权重15%）基础设施 + 智能客服 Agent

| 功能 | 说明 | 验收标准 |
|---|---|---|
| F1.1 项目基础框架 | FastAPI 分层架构（api/service/tool/model/config/utils）、MySQL 10张表建表、Redis连接、MinIO文件上传、统一响应格式、全局异常处理、分级日志 | Swagger可访问；10张表全部建成 |
| F1.2 RAG知识库 | 文档解析(txt/md/docx)→分块(512token/overlap64)→Embedding入Milvus（FAQ/产品/政策3个集合）→元数据存MySQL；增删查改接口 | 知识库管理增删查正常；FAQ检索准确 |
| F1.3 智能客服Agent | `POST /api/chat/customer`；5类意图（产品咨询/政策解读/FAQ/闲聊/转人工）；RAG检索+LLM生成+来源引用；Redis短期记忆(30min TTL/4096token)；Score<0.7兜底转人工；"转人工"意图落地为写入`biz_work_order`（`order_type=客户转介`），由理财顾问/客户经理领取处理，Mock真实电话/线下联系（见需求文档2.4.1节） | 产品咨询准确率≥80%（5题+）；政策解读2题+；多轮对话3轮+上下文不丢失 |

### Phase 2（权重20%）客户画像 + 数据分析 Agent

| 功能 | 说明 | 验收标准 |
|---|---|---|
| F2.1 客户画像系统 | 从对话LLM抽取标签写入`fin_customer_profile`+Redis缓存；四维度加权打分（基础属性25%+投资经验25%+风险偏好30%+行为异常20%）→C1-C5；硬性熔断（年龄/无收入低资产/风评过期）；冲突处理策略（高置信度覆盖低置信度） | 5位测试客户画像输出正确；熔断规则边界case生效 |
| F2.2 风险评估模块 | 16题风评问卷→总分判C1-C5(0-20/21-40/41-60/61-80/81-100)；适当性匹配检查（C等级 vs R等级） | 问卷判等级正确；适当性检查阻止C1购R4 |
| F2.3 数据分析Agent（NL2SQL） | `POST /api/chat/analyst`；动态Schema筛选+few-shot→LLM生成SQL→安全校验（仅SELECT，正则拒绝DROP/DELETE/UPDATE/INSERT/ALTER/TRUNCATE）→执行(限100行)→自然语言解读 | 准确率≥80%（5题+）；安全校验拒绝危险SQL |

### Phase 3（权重20%）知识图谱 + 投顾/业务操作 Agent

| 功能 | 说明 | 验收标准 |
|---|---|---|
| F3.1 Neo4j知识图谱 | 节点(Customer/Product/RiskLevel/Industry/Market/FundManager)、关系(INVESTS_IN/BELONGS_TO/MANAGED_BY/SUITABLE_FOR等)；从MySQL导入+Mock行业数据 | 节点数>100、关系数>200 |
| F3.2 GraphRAG增强检索 | 实体识别→Neo4j多跳查询→融合排序（向量Score×0.6+图谱Score×0.4） | GraphRAG效果优于纯RAG（对比测试） |
| F3.3 投顾助手Agent | `POST /api/chat/advisor`；读画像→适当性过滤→图谱增强（避免行业集中）→多因子排序（收益0.3/风险匹配0.25/期限0.15/分散度0.15/图谱信号0.15）→推荐理由生成；资产配置建议 | 推荐符合风险等级（C1不推R4+） |
| F3.4 业务操作Agent（NL2API） | `POST /api/chat/operator`；**客户不可直接访问，由理财顾问（申购/赎回/风评重做）和客户经理（转账/信息更新/工单创建）代客户操作**，全系统唯一写操作入口；8种意图；Function Calling参数提取；RBAC权限校验；二次确认（申购>1万/转账>5万） | 意图识别准确率>80%（10用例+）；参数提取>90%；无权限操作拒绝 |

### Phase 4（权重20%）风控预警 + 记忆体系

| 功能 | 说明 | 验收标准 |
|---|---|---|
| F4.1 风控监测Agent | 20条规则（基于反洗钱可疑交易识别规则RW-001~020）双轨触发：8条实时/准实时规则（RW-001/003/008/011/014/015/016/017）消费`stream:large_transaction`/`stream:suspicious_intent`事件回查源表判定，12条日批/周批规则由APScheduler定时批量扫描；分级（1条→蓝/2-3条或重复→黄/>3条→红）；写`fin_risk_alert`+`biz_work_order`双表；生产`stream:risk_alert` | 20条规则正确匹配（10测试交易+，覆盖实时与批量两类）；三级分级正确；Streams生产/消费/ACK正常，定时批量任务按cron周期正确触发（需求文档2.4节，已从Pub/Sub改为Streams） |
| F4.2 三层记忆架构 | 短期(Redis会话，30min TTL)、中期(MySQL+Redis画像/工单)、长期(Milvus+Neo4j+MinIO知识/图谱) | 三层各自工作正常；会话归档完整 |

### Phase 5（权重15%）系统集成 + 联调优化

| 功能 | 说明 | 验收标准 |
|---|---|---|

## 3. 五大 Agent 职责矩阵

| 维度 | 智能客服 | 投顾助手 | 风控监测 | 数据分析 | 业务操作 |
|---|---|---|---|---|---|
| 服务对象 | 客户 | 理财顾问 | 风控专员 | 内部员工 | 理财顾问、客户经理 |
| 核心能力 | 知识问答 | 产品推荐 | 异常检测 | NL2SQL查数 | NL2API执行操作 |
| 关键技术 | RAG+短期记忆 | GraphRAG+中期记忆 | 规则引擎+置信度 | NL2SQL | NL2API+RBAC |
| 触发方式 | 主动交互 | 主动交互 | **双轨被动触发**（实时/准实时规则：事件流触发；日批/周批规则：APScheduler定时批量扫描，见需求文档2.4节） | 主动交互 | 主动交互 |
| 安全等级 | 低（只读） | 中（涉及推荐） | 高（涉及预警） | 中（涉及数据） | 高（涉及写操作） |

> **五个Agent里客户实际只直接对话1个**：只有智能客服Agent服务对象是客户本人，其余4个（投顾助手/风控监测/数据分析/业务操作）都是员工侧工具。理财顾问会横跨投顾助手Agent（只读推荐）和业务操作Agent（写操作执行）两个：先用前者做产品推荐，客户确认后同一位理财顾问切到后者执行申购/赎回，两步顺序发生、职责不重叠。客户经理不经过投顾助手Agent，直接用业务操作Agent处理转账/信息更新/工单创建。客户从"有购买意向"到"被理财顾问服务"之间的连接，靠客服Agent写入`biz_work_order`客户转介工单来Mock（见需求文档2.4.1节），而非真实电话/线下联系。

所有 Agent 共享同一套抽象骨架 `AgentBase.handle()`：输入接收→短期记忆召回→中期记忆召回→长期记忆召回→意图路由→置信度重排→核心逻辑→工具调用→结果生成→流式输出→数据沉淀→事件广播。子类只需实现 `classify_intent()` / `_get_handler()` / `_intent_threshold()` / `_scenario_name()` 四个方法。跨 Agent 不直接调用，统一走 Redis Pub/Sub 事件总线（`event:risk_alert`、`event:large_transaction`、`event:suspicious_intent`）。

## 4. 技术栈与用途

| 组件 | 用途 |
|---|---|
| Python 3.10+ / FastAPI | 后端框架 |
| MySQL 8.0 | 10张核心业务表 |
| Milvus 2.x | RAG向量检索（FAQ/产品/政策3集合，1024维，bge-large-zh或同等） |

## 5. API 接口清单（需求文档6.6节）

- **对话**：`POST /api/chat`（统一入口）、`/api/chat/customer`（客户使用）、`/api/chat/advisor`（**理财顾问专用**）、`/api/chat/analyst`（**内部员工专用**）、`/api/chat/operator`（**理财顾问/客户经理专用，客户不可访问**）、`GET /api/chat/session/{id}/history`、`GET /api/chat/stream`(SSE)
- **知识库**：`POST /api/knowledge/upload|search`、`GET /api/knowledge/list`、`DELETE /api/knowledge/{id}`
- **画像**：`GET|PUT /api/profile/{customer_id}`、`POST /api/profile/{customer_id}/assessment`、`GET .../assessment/history`
- **产品**：`GET /api/product/list|{id}`、`POST /api/product/recommend`
- **业务操作**（**员工专用，代客户操作**）：`POST /api/operation/purchase|redeem|transfer`、`PUT /api/operation/contact`
- **风控**：`POST /api/risk/monitor`、`GET /api/risk/alerts`、`PUT /api/risk/alert/{id}/handle`
- **工单**：`POST /api/workorder`、`GET /api/workorder/list`、`PUT /api/workorder/{id}`
- **图谱**：`GET /api/graph/stats|visualization/{customer_id}`
- **管理**：`POST /api/admin/recalculate-confidence`
- **认证**：`POST /api/auth/login`

另有 **10个内部 Tool**（非REST，供Agent调用）：MemoryValidator、BaseConfidenceCalc、FinalConfidenceRank、KnowledgeRetrieval、GraphQuery、NL2SQL、NL2API、RiskRuleMatch、ProfileExtract、SuitabilityCheck。

## 6. 数据模型要点

**MySQL 10表**：`base_user`（脚手架自带用户表，客户+员工统一表，需补充`employee_role`/`customer_level`两列而非另建平行表）、fin_customer_profile、fin_product、fin_transaction、fin_holdings、fin_risk_assessment、fin_risk_alert、biz_work_order（含`order_type`枚举，其中"客户转介"用于Mock客户-员工交接，见需求文档2.4.1节）、conversation_archive、fin_knowledge_meta。

**Neo4j**：节点 Customer/Product/RiskLevel/Industry/Market/FundManager；关系 HAS_RISK_LEVEL/INVESTS_IN/BELONGS_TO/MANAGED_BY/SUITABLE_FOR/LOCATED_IN。

**业务规则数据来源**（可直接转化为规则引擎/画像模型参数，见业务素材分析）：
- 产品风险分级 R1-R5、客户风险分级 C1-C5，匹配矩阵与豁免/双录/冷静期条件 → 来自《个人投资者适当性管理指南》《理财产品销售管理办法》
- 20条反洗钱可疑交易规则(RW-001~020) → 来自《反洗钱可疑交易识别规则》，可直接映射为 F4.1 的规则引擎
- 四维度画像打分公式与熔断规则(FM-01~05) → 来自《投资者风险画像研判规则》，直接对应 F2.1
- 高净值分层(金卡/白金/钻石/私行)与升降级规则 → 来自《高净值客户服务规范》
- 测试客户A(高净值/C4)、客户B(普通/C1) → 作为端到端测试用例（Phase 5 F5.2）

## 7. 需要团队确认的疑点/文档间差异

这些是通读过程中发现的**未明确或存在潜在冲突**的地方，建议在下一次需求评审会上过一遍：

1. **风控置信度公式未落地**：《功能设计文档》第4章只给出 `_calc_risk_confidence(triggered_rules, is_repeat)` 的调用签名（"单规则=低/多规则=中/多源=高"的定性描述），没有具体计算公式；《需求文档》F4.3 给出的是"记忆置信度"公式（来源初值+证据-冲突×时间衰减），两者是否是同一套还是风控要单独设计，需要团队决定。
2. **记忆体系细节留白**：《记忆架构设计》定位是"教学指南"而非规格书，`MemoryUnitValidator`（六维校验）、`MemoryStore`（存储封装）、`recall_memories()` 里的综合重排公式（置信度+语义相关性+场景权重+时效性如何加权）均未给出可执行细节，需要开发时自行设计并在《表设计文档》/《API接口文档》中补全。
3. **意图置信度阈值只给了客服Agent的示例(0.6)**，投顾/风控/数据分析/业务操作各自的阈值文档未逐一列出具体数值，需要开发时统一定义并写入配置。
4. **GraphRAG信号强度 `graph_signal`（投顾多因子排序里占15%权重）的具体计算方法未展开**，只知道是"图谱增强信号"，需要设计具体量化方式（如同行业集中度、关联度分数等）。
5. **反洗钱规则文档与适当性管理文档存在交叉引用**（如双录触发条件、大额交易报告标准在两份文档中都有出现但口径略不同），构建规则引擎时需要去重合并，避免同一交易被两套规则重复判定或口径冲突。
6. **业务素材中含大量"XX""20XX"脱敏占位符**（属虚构测试数据），实际接入RAG知识库时提示词需要处理好，避免模型把占位符当真实数值引用给用户。

## 9. 团队协作与交付要求（答辩相关，非功能性但需并行推进）

> 以下评分权重按老师原始文档的 Phase 分组照抄，用于对照验收标准，**不代表团队按5周排期开发**——实际4天开发的任务顺序按脚手架复用程度重新排定，见需求文档1.5节与《脚手架复用能力盘点.md》。

- 文本交付物：每日会议纪要、开发计划、表设计文档、API接口文档、答辩PPT、需求文档
- Git分支策略(main/develop/feature/xxx) + Conventional Commits；核心模块需1人review后合并
- 评分：Phase1 15% / Phase2 20% / Phase3 20% / Phase4 20% / Phase5 15% / 答辩10%；每Phase=功能完整性60%+代码质量20%+文档规范20%；加分项最高+20（架构+5/创新+5/RAG效果+3/GraphRAG深度+3/前端体验+2/代码质量+2）；扣分项含项目无法启动-20、核心功能缺失-10/项、适当性违规-10、安全事故-10
- 答辩要求：主讲人+协助人，15分钟内，重点讲思路而非常规代码，需演示RAG/GraphRAG/NL2SQL/NL2API四类场景，必问"是否用了Vibe Coding、踩过什么坑"
