## 0. 文档说明

- 本文档是《表设计文档.md》§1.10（`fin_knowledge_meta`）与§4（Milvus 4个集合）的**执行层展开**：前者定义了"知识要落在哪张表/哪个集合"，本文档定义"素材原文怎么变成一条条能检索准的向量记录"。

- 责任人：负责人（F1.2 RAG入库/知识库管理）。4天工期取向：一次性离线批处理脚本，不做管理后台实时上传界面（`fin_knowledge_meta.uploaded_by`用固定的系统/管理员账号占位即可）。

## 2. 总体流水线

```
源文件(.txt/.md)
   │
   ▼
① 占位符清洗（regex+词典替换，见§4）──→ 产出 {文件名}_cleaned.md/txt（保留原文件不动）
   │
   ▼
② 分文件类型切片（见§3）──→ 产出内存中的 chunk 列表，每条 chunk = {title, content, extra_fields}
   │
   ▼
③ 幂等性检查（见§5）：查 fin_knowledge_meta WHERE source_file=? AND title=? AND status='已入库'
   │  已存在且内容hash未变 → 跳过
   │  已存在但内容hash变化 → 旧记录 status→已下线 + 删除对应Milvus向量，走④插入新记录
   │  不存在 → 走④插入新记录
   ▼
④ 逐chunk处理：
   a) 原始（清洗后）文件整体存一份到 MinIO（bucket=fin-knowledge-raw，Key见表设计文档§5）
   b) chunk.content 调本地 Ollama bge-m3 生成 embedding（1024维，调`ollama_embedding()`）
   c) 写入 MySQL fin_knowledge_meta，status='待入库'，拿到自增id
   d) 写入对应 Milvus 集合（BaseVDBModel.insert，content_sparse由Milvus BM25函数从content自动生成，不用脚本算）
   e) 用Milvus返回的主键回填 fin_knowledge_meta.milvus_pk，status更新为'已入库'
   │
   ▼
⑤ 跑完后人工抽检：每个集合随机抽5条chunk，用原始FAQ问题/产品名/政策条款反查，确认检索TopK能命中
```

第④步c/d/e是脚本里的一个事务性小函数（先MySQL占位、再Milvus写入、成功后回填状态），任何一步失败整条chunk标记异常并打日志，不影响其他chunk继续处理——4天工期不做分布式事务，允许"至多再跑一次脚本"来补齐失败的chunk（脚本本身通过§5的幂等检查天然支持重跑）。

## 3. 分文件类型切片规则

### 3.1 FAQ类：`高频问答对.txt`

文件格式是制表符分隔的三列：`序号\t问题\t答案`（共39行，无表头）。

- **切片粒度**：1行 = 1个chunk，不做任何合并或拆分——每条FAQ本身就是一个完整语义单元，拆开或合并都会破坏"一问一答"的检索精度。
- **Embedding对象**：只对`question`做embedding（对应`fin_faq_collection`是纯稠密检索，TopK3/阈值0.75，靠"用户问题"与"库中问题"的相似度匹配，`answer`不参与向量计算，检索命中后直接把`answer`原文返回给Agent拼进RAG上下文）。
- **字段映射**：

| chunk字段 | 来源 | 写入位置 |
|---|---|---|
| `title` | 取问题原文（截断至100字内） | `fin_knowledge_meta.title` |
| `question` | 原文第2列（清洗后） | `fin_faq_collection.question`，embedding源 |
| `answer` | 原文第3列（清洗后） | `fin_faq_collection.answer` |
| `source_file` | `高频问答对.txt` | `fin_knowledge_meta.source_file` |

### 3.2 产品说明类：`个人理财产品手册.md`

Markdown三级标题结构：`## 一、基金类产品` → `### 1.1 XX货币市场基金`（含参数表格+投资策略+适合人群） → `### 1.2 ...`，另有`## 四、产品对比表与推荐策略`/`## 五、申购赎回操作流程`/`## 六、费率说明`三个跨产品的通用小节。

- **切片粒度**：以`###`三级标题为主切分单元——每个产品的"参数表格+投资策略+适合人群"三段合在一起是一个完整语义单元（拆开会导致检索到孤立的参数表却丢了"适合谁买"的关键信息，这是产品推荐场景最需要的部分）。单个产品段落约600-1200字，远低于VARCHAR(65535)上限，也在Embedding模型有效窗口内，不需要二次拆分。
- `## 四/五/六`三个通用小节没有具体`product_id`可关联，仍按`###`小节切分（如"4.1 产品对比表"、"5.1 申购流程"、"6.1 费率总览"），`product_id`留空，靠`content`本身的语义检索命中。
- **Embedding对象**：对`content`（清洗后的整段markdown文本，含表格）做embedding，同时利用`fin_product_collection`的混合检索（稠密0.7+BM25稀疏0.3），BM25那一路能兜住"风险等级R2"“起投金额1000元”这类关键词精确匹配，弥补纯语义检索对表格数值不敏感的问题。
- **字段映射**：

| chunk字段 | 来源 | 写入位置 |
|---|---|---|
| `title` | `###`标题原文，如"1.2 XX稳健增利债券A" | `fin_knowledge_meta.title` |
| `product_id` | 若该产品已在`fin_product`表登记（见表设计文档§1.3），按产品代码/名称关联；四/五/六节留NULL | `fin_product_collection.product_id` |
| `content` | 该`###`小节全文（含表格markdown原文，清洗后） | `fin_product_collection.content`，embedding源 |
| `source_file` | `个人理财产品手册.md` | `fin_knowledge_meta.source_file` |

> `fin_product`表与`fin_product_collection`是两个不同粒度：前者是结构化产品主数据（给下单/持仓等业务逻辑用），后者是给RAG检索用的文本切块，`product_id`是两者之间唯一的关联桥梁，避免同一产品的"结构化字段"和"自然语言说明"两处数据不一致时无法互相印证。

### 3.3 政策法规类：`反洗钱合规操作手册.md` / `个人投资者适当性管理指南.md` / `理财产品销售管理办法.md` / `反洗钱可疑交易识别规则.md` / `投资者风险画像研判规则.md`

五份文件结构一致：`## 第X章 章名` → `### 第X条 条名` → 可能还有`#### X.X 小节名`（如反洗钱手册"第五条"下有5.1/5.2/5.3三个小节）。

- **切片粒度**：以`###`（条，或`反洗钱可疑交易识别规则.md`里的"规则RW-XXX"）为主切分单元，这是法规文档天然的最小完整语义单元（一条/一条规则对应一项具体要求，检索命中后可以直接作为"依据第X条"或"依据RW-XXX"引用）。
  - 若某条正文（含其下所有`####`小节）超过约1500字（如反洗钱手册"第五条"这种带表格+多个小节的长条），按`####`小节进一步拆分，每个小节单独成chunk，避免单条内容过长稀释向量语义、拉低检索精度。
  - 若某条本身很短（如"第二条 适用范围"只有几行列举项），不与相邻条合并——保持"一条一chunk"的可追溯性优先于避免过短chunk。
- **上下文前缀**：每个chunk的`content`前面拼接"所属章标题+条标题"作为前缀，如：

  ```
  【第二章 客户身份识别（KYC）要求】第五条 开户环节身份核实
  5.1 自然人客户身份核实
  自然人客户办理开户时，应核实以下信息...
  ```

  原因：政策条款单独抽出来往往缺主语（"应核实以下信息"——核实什么场景下的谁？），检索命中后如果不带章/条标题上下文，Agent组装回答时容易断章取义；拼前缀是最低成本的解决办法，不需要额外的父子chunk关联机制。
- **Embedding对象**：对拼接前缀后的`content`整体做embedding，同样走`fin_policy_collection`的混合检索（稠密0.7+BM25稀疏0.3）——政策法规场景经常需要精确匹配"5万元"“25%”“90天”这类监管红线数值，BM25稀疏检索对这类数值/术语的召回明显优于纯稠密向量。
- **字段映射**：

| chunk字段 | 来源 | 写入位置 |
|---|---|---|
| `title` | "第X条 条名"，如"第五条 开户环节身份核实" | `fin_knowledge_meta.title` |
| `policy_source` | 文件名，如"反洗钱合规操作手册.md" | `fin_policy_collection.policy_source` |
| `content` | 章/条前缀 + 条文（含其下小节，清洗后） | `fin_policy_collection.content`，embedding源 |
| `source_file` | 同`policy_source` | `fin_knowledge_meta.source_file` |

## 4. 占位符清洗规则（呼应《待确认疑点补充设计建议.md》疑点6）

源素材里"XX科技"“20XX年”“XXX亿元”这类占位符在9个文件里反复出现且指代同一实体（同一个公司、同一个网址），如果不做清洗直接切片入库，检索命中后原样吐给客户会显得非常不专业（用户会看到"欢迎致电XX科技客服热线400-XXX-XXXX"这种明显未完成的文本）。分两层处理，与疑点6原方案一致：

### 4.1 离线清洗脚本（第一层，覆盖率主力）

维护一份**跨文件统一**的占位符替换词典，入库前对5个待入库源文件做一次性regex替换，产出`_cleaned`副本（原文件保留不动，供审计对照）。词典覆盖反复出现、需要跨文件保持一致的实体：

| 占位符原文 | 统一替换值 | 出现文件举例 |
|---|---|---|
| `XX科技（有限公司）` | 锦鹏科技有限公司 | 9个文件均有出现 |
| `XX Tech Co., Ltd.` | Jinpeng Tech Co., Ltd. | 企业信息.md |
| `www.xxtech.com` | www.jinpengtech.com | 高频问答对.txt等 |
| `400-XXX-XXXX` | 400-822-6699 | 高频问答对.txt、企业信息.md |
| `某市` | 临江市 | 企业信息.md、反洗钱手册等 |
| `20XX年X月XX日`（成立时间，需与"运营超过10年"等描述互相一致） | 2014年6月18日 | 企业信息.md、高频问答对.txt |
| `X亿元（XX,XXX万元）`（注册资本） | 8亿元（80,000万元） | 企业信息.md |
| `X,XXX人`（员工人数） | 3,200人 | 企业信息.md、新人指南（不入库但保留一致性） |

该词典是**面向5个入库文件**的正式实现物料，作为脚本配置文件（如`placeholder_dict.json`）维护，落地时按9个源文件实际出现的全部占位符逐条补全，本文档只列代表性条目说明替换规则的粒度和跨文件一致性要求。

区分两类占位符，替换策略不同：
- **跨文件重复出现、指代同一实体**（公司名/网址/热线/成立时间/注册资本等）→ 必须用同一份词典统一替换，否则同一公司在FAQ里叫"锦鹏科技"、在政策文件里还是"XX科技"，检索结果拼一起会自相矛盾。
- **单文件内单次出现的数值占位符**（如产品手册里每个产品各自的"基金规模XXX亿元”“近一年收益率X.XX%"）→ 不需要跨文件一致性，清洗脚本按所在表格上下文规则生成一个数值区间内的合理示例值即可（如风险等级R1的产品收益率填1%-3%区间内的值），不用词典维护。
- **人名占位（"张某”“李某”“王某”“陈某"）→ 不清洗**：这是源素材本身的合规脱敏写法（真实政策文件审核人/批准人也常用"某"代称），不是未完成的占位符，保留原样。

### 4.2 Prompt层兜底检查（第二层，防漏网）

清洗脚本不保证100%覆盖（新增素材、脚本规则没覆盖到的边缘写法）。客服Agent的RAG系统提示词里加一道兜底规则：检索到的chunk拼入上下文前，用简单regex（`XX+`连续大写X、`20XX`、`X,XXX`等模式）扫一遍检索结果，命中则在生成前触发告警日志（不阻断回答，避免误伤合法的"XX"缩写场景，如"QDII"），供后续人工回补清洗词典——这一层是安全网而非主力，主力清洗必须在入库前的离线脚本完成。

## 5. 幂等性与更新/下线流程

`fin_knowledge_meta`没有版本号字段，用`status`状态机 + 重跑脚本实现幂等：

- **首次入库**：`source_file`+`title`组合不存在 → 正常走§2④插入。
- **重跑脚本（源文件未变）**：`source_file`+`title`已存在且`status='已入库'` → 跳过，不重复写Milvus（避免同一chunk在集合里出现多条重复向量，拉低检索TopK的有效位数）。
- **源文件内容更新**（如政策文件修订）：脚本对比清洗后文本的内容hash（存一份`content_hash`在脚本本地缓存，不入MySQL——4天工期不为此单独加字段），hash变化则：
  1. 旧记录`status`置为`已下线`（不物理删除MySQL行，保留审计轨迹）；
  2. 从Milvus按`milvus_pk`删除对应向量；
  3. 按§2④插入新chunk，得到新的`fin_knowledge_meta`行和新的`milvus_pk`。
- **下线**：源文件被移出知识库范围（如后续把"高净值客户服务规范.md"纳入二期），对应全部chunk批量`status→已下线`+ Milvus删除，MinIO原文件保留不删。
