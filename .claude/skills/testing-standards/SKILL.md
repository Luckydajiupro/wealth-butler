# 测试规范

本规范是《Vibe Coding协作规范.md》§3 的落地。4 天工期下不追求覆盖率数字，追求"关键路径不翻车"。

## 1. 测试框架

- 一律使用 pytest，沿用脚手架现有约定（参照 `Repository/test/`、`Ai/base/test_*.py` 的写法）。
- 禁止引入新测试框架。

## 2. 覆盖优先级（从高到低）

1. 《开发计划.md》标 🔑 的 7 项关键路径任务，每项至少有一个能跑通的最小验证用例：
   - NL2Cypher 查询生成、NL2SQL 全链路（含安全校验）、三层记忆置信度体系、风控规则引擎+适当性匹配、跨 Agent 事件总线、多 Agent 协作编排、10 张业务表+8 个业务 API 的业务逻辑。
2. 20 条风控规则——每条至少 1 个"应该命中"+1 个"不应该命中"的边界 case（参照需求文档 §9.1，10 测试交易以上）。
3. NL2SQL 安全校验层——必须有"尝试注入危险 SQL 被正确拦截"的用例，不能只测正常查询能跑通。
4. 二次确认状态机（"待确认→已确认→执行"）——`confirm` 和 `cancel` 两条路径都要覆盖。

## 3. 谁写测试

谁写业务逻辑谁写对应测试，不设专职测试人员。李清华 Day4 上午的端到端联调本身就是系统级测试，不需要重复造轮子。

## 4. 测试代码的命名与落点

- 测试文件放对应模块的 `test/` 目录，或与源文件同目录下 `test_*.py`，沿用脚手架现有约定。
- 测试函数命名清晰表达测的是什么规则/场景，避免 `test_1`、`test_2` 这类无意义命名。

## 5. 交付前自检

对照本节覆盖优先级，确认本次改动涉及的关键路径/风控规则/安全校验/状态机有没有对应测试；没有则补，不要"代码写了测试没写"就提交。
