# 文档版本与变更管理

本项目文档多、变更频繁，若版本号与变更记录不维护，几天后团队和答辩评委都说不清每份文档当前是什么状态。**任何文档改动，都必须同步更新版本号 + 变更记录。**

## 1. 版本号维护

- 每份文档维护一个版本号，放在文档开头（文档说明附近，如"版本：v1.0"）。
- 格式：`v{主}.{次}`。
- 递增规则：
  - **实质性内容变更**（字段、接口、规则、架构、口径调整）→ 递增，小改 `v1.0→v1.1`，结构性大改 `v1.x→v2.0`
  - **纯措辞/格式微调** → 可不升版本号，但变更记录仍要记
- 新文档首版为 `v1.0`。

## 2. 变更时必做的三件事

1. **更新版本号**（按 §1 规则）
2. **变更记录表追加一行**：`日期 | 变更内容 | 变更人`——变更人必须填**实际人名**，不得留"（待填）"
3. **若波及其他文档**：联动更新受影响文档（见 doc-consistency §2 联动场景），同步升版本号 + 记变更记录

## 3. 变更内容怎么写

- 写"改了什么 + 为什么"，能看出这次变更的背景（例如"风控双轨触发由 5条/15条 改为 8条/12条，原因：RW-011/014/015 字段已存在且标注为实时"），不要只写"修正口径"这种无信息量描述。
- 涉及多文档的同一变更，各文档的变更记录里写同一句话（方便跨文档对照），或相互引用。

## 4. 协作约定

- **谁改谁登记**：改动文档的人负责在对应文档的变更记录里填自己的名字（配合 merge-standards"只改自己文件"铁律）。
- **每日核对**：每天日终（当日会议纪要时），对当天动过的文档统一核对一遍版本号是否都升了、变更人是否都填了。
- **历史遗留**：现有文档变更记录的"（待填）"是历史欠账，Day1 起逐步回填（按《开发计划.md》§1 分工表推断责任人，或由李清华统一回填）。

## 5. 交付前自检

- 本次文档改动是否升了版本号？
- 变更记录是否追加了（含变更人实名）？
- 是否波及其他文档、它们是否也升号+记变更？
- 变更内容描述是否说明了"改了什么 + 为什么"？
