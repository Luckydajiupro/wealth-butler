# 测试用例生成

本规范是《Vibe Coding协作规范.md》§4 的落地。鼓励用 AI 生成测试用例草稿（比手写快），但生成后必须对照权威来源核对完整性，不能全信 AI 自己想的 case。

## 1. 生成测试用例时的必带上下文

让 AI 生成测试用例前，把设计规格喂给它，不要让它凭空猜：

- 风控规则类 → 附上《研判规则提取与落地方案.md》对应规则条目 + 项目根目录《用户研判规则》原始规则文本
- 接口类 → 附上《API接口设计文档.md》对应接口的请求/响应契约

## 2. 生成后必须核对的两个来源

生成草稿后，逐条核对完整性：

- **风控规则类**：对照《研判规则提取与落地方案.md》和《用户研判规则》原始文本，确认边界值覆盖到了（例如">1万"是否包含 1万整这种细节、RW 规则的触发窗口）。
- **接口类**：对照《API接口设计文档.md》，确认异常路径有覆盖（401 无权限、403 权限不足、参数校验失败），不是只测 happy path。

## 3. 测试数据

- 优先复用项目《用户测试数据》里的客户 A / 客户 B 两个样本。
- 但《开发计划.md》Day3 任务已提醒：不能只用 A/B 两个真实样本，边界 case 需要团队自己额外构造。

## 4. 用例的组织

- 按"应该命中 / 不应该命中"成对组织，尤其是风控规则（每条至少 1 正例 + 1 反例）。
- 安全校验类必须包含"注入被拦截"的负例（见 testing-standards 第 2.3 条）。

## 5. 交付前自检

确认生成的用例已覆盖 §2 两个核对来源、§3 的测试数据要求、§4 的正反例组织，再提交；有遗漏当场补，不留到 review 阶段才发现。
