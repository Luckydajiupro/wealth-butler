# 代码 review 规范

本规范是《Vibe Coding协作规范.md》§1.1 的落地。团队工作流：Codex 写代码 → 各人合并到主分支 → 合并后 Claude Code 统一 review。

## 1. 时机

- review 不是写代码阶段的即时门禁，而是代码合并完成后对主分支的一次整体质量把关。
- 统一 review 时暂停新代码写入，避免"边审边有人往主分支推新代码"导致 review 结果失真。

## 2. 重点（覆盖《Vibe Coding协作规范.md》§1 列出的关键场景）

逐行确认以下四类高风险代码：

- **金额**：计算、校验、二次确认阈值（申购>1万 / 转账>5万）是否正确。
- **权限校验**：接口是否真的挂了 RBAC，权限字符串与《Agent设计文档.md》§5.1 意图分类一致。
- **风控规则阈值**：20 条规则（8 条实时/准实时 + 12 条日批/周批）的判定条件与《研判规则提取与落地方案.md》一致。
- **SQL/Cypher 拼接**：尤其确认 SQL 白名单校验真实存在且生效——Codex 最容易照抄脚手架里不做表名/字段白名单的 `SQLBuilder` 不安全模式。

## 3. 通过判定标准

review 通过的代码必须同时满足：

- 字段 / 接口路径与《表设计文档.md》《API接口设计文档.md》对齐
- 命名符合 coding-standards（小驼峰、落点正确）
- 关键路径有对应测试（对照 testing-standards 覆盖优先级）
- 无硬编码密钥
- 各人只改了自己负责的文件（对照《开发计划.md》§1 分工表，防越界改动别人模块）

## 4. 交叉一致性核对

review 时顺带核对跨文档一致性，防止 AI 改了 Model 字段但没同步改调用处：

- Model 字段变更 → 检查 Repository/Service 调用处是否同步
- 权限字符串变更 → 检查《Agent设计文档.md》§5.1 与《API接口设计文档.md》是否同步
- 规则阈值变更 → 检查《研判规则提取与落地方案.md》是否同步

## 5. 输出

review 结束后给出结论：通过 / 需要修改（列出具体问题点 + 对应文件 + 修改建议）。需要修改的问题点按"是否阻塞演示"分级，先修阻塞项。
