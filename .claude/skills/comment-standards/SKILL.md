# 代码注释规范

本规范规定代码注释的语言、原则与必须注释的场景。注释的读者是**刚接触大模型开发的团队成员**，以及答辩现场的评委——注释的首要任务是帮一个不熟悉 Agent/RAG/NL2SQL 这些概念、也不熟悉脚手架的人，看懂代码在做什么、为什么这么做。因此注释要合理充分，不能只写最少的 WHY 而不解释 WHAT。

## 1. 注释语言

- 注释用中文（团队与答辩均为中文语境）。
- 标识符、变量名、函数名仍用英文小驼峰（遵守 coding-standards），注释负责用中文把这些标识符"翻译"给新手看，说明它的业务含义。

## 2. 核心原则：WHAT 和 WHY 都要写

- **WHAT**：对新手来说，"看懂这段代码在干什么"本身就是难点。关键逻辑段要写清楚它做了什么，尤其是涉及大模型开发特有概念的地方。
- **WHY**：业务规则、隐藏约束、对脚手架的改造、踩坑修正，这些从代码本身看不出来，必须写。
- 判断标准不是"删掉会不会困惑"（新手几乎对什么都困惑），而是"**这段代码对理解整体逻辑是否关键**"——关键就写，纯样板就不必逐行写。

## 3. 必须写注释的场景

以下场景要写注释（对新手尤其重要）：

1. **大模型开发特有概念**：Agent、工具调用（Function Calling）、Prompt、向量检索/Embedding、事件总线（Streams）、中间件洋葱模型、NL2SQL 白名单校验、GraphRAG 融合排序等——这些概念新手不熟，首次出现或每次核心用法处都要注释说明"这是什么、在流程里起什么作用"。
2. **非显而易见的业务规则**：风控规则阈值判定、置信度计算公式、适当性匹配（C vs R）、二次确认阈值（申购>1万 / 转账>5万）。示例：`# RW-011 仅以事件作触发信号，命中后回查源表按 30 天窗口判定，不维护 Redis 计数器`
3. **脚手架复用 / 改造点**：新手不知道脚手架原样，要注明"这里是直接复用的（原样）"还是"这里改过了（原样是 X，改成 Y，因为 Z）"——后者直接对应答辩"为什么这样设计"的追问。
4. **较长方法的关键步骤分段**：一个超过十几行的方法，用注释给关键步骤做分段引导，帮新手跟上思路（例如一个风控规则：取数 → 判定 → 写预警 → 发事件，每段一行注释）。
5. **踩坑修正点**：AI 曾生成错误代码、后来修正的地方，注释留一句"原实现是 X，因 Y 问题改为 Z"——这是答辩"错误尝试→修正"的素材。

## 4. 不必逐行注释的场景

以下场景不必逐行写，但可以在一段代码上方写一句总起注释（帮新手概括这一段在干什么）：

- 纯样板 CRUD（Model 字段定义、简单增删改查）
- 自解释的赋值、显而易见的循环/判断
- 与脚手架里既有写法完全一致的代码（指向参照文件即可，不必重复解释）

## 5. 注释风格

- 中文，简短但完整，一句说清。
- 行内 `# ...` 解释单行/单个关键判断；函数或代码段上方的一行 `# ...` 概括整段作用。
- 可以用多行注释给"关键路径攻坚"这类复杂模块在文件开头写一段 3~5 行的模块说明（这个模块是干嘛的、属于哪个关键路径、核心设计点），帮助新手和评委快速建立全局认识。
- 不用 emoji，不写"新增 / 用于 X 流程"这类会随代码演化失效的临时性注释。

## 6. 交付前自检

对照 §3 五类场景，确认本次改动涉及的大模型概念 / 业务规则 / 脚手架改造 / 关键步骤分段 / 踩坑修正有没有写注释；站在"刚接触大模型开发的新手"视角通读一遍，哪里看不懂就补注释，再提交。
