1. Agent 设计总览

1.1 统一执行骨架

所有 Agent 共享同一个执行骨架。这不是"5 个独立系统"，而是"1 个骨架 + 5 个策略配置"。统一骨架的好处在于：错误处理、日志、链路追踪、记忆召回、流式输出等基础设施只需实现一次，每个 Agent 只需定义自己的意图分类器、工具集和回复策略。

骨架伪代码：

python · 统一骨架
class AgentBase(ABC):
    """所有 Agent 的抽象基类"""

    def __init__(self, agent_type: str, memory: MemoryOrchestrator,
                 tools: list[BaseTool], llm: LLMClient):
        self.agent_type = agent_type
        self.memory = memory
        self.tools = {t.name: t for t in tools}
        self.llm = llm

    async def handle(self, request: ChatRequest) -> ChatResponse:
        """统一入口 — 不可被子类覆写"""
        # 1. 召回记忆
        context = self.memory.recall(
            customer_id=request.customer_id,
            scenario=self._scenario_name(),
            query=request.message,
            top_k=5
        )

        # 2. 意图分类
        intent = await self.classify_intent(request.message)

        # 3. 置信度校验
        if intent.confidence < self._intent_threshold():
            return self._clarify(request.message)

        # 4. 路由到具体处理逻辑
        handler = self._get_handler(intent)
        result = await handler(request, context)

        # 5. 归档 + 广播
        self.memory.archive(request, result)
        await self._maybe_broadcast(result)

        return result

    @abstractmethod
    async def classify_intent(self, message: str) -> Intent: ...

    @abstractmethod
    def _get_handler(self, intent: Intent) -> Handler: ...

    @abstractmethod
    def _intent_threshold(self) -> float: ...

    @abstractmethod
    def _scenario_name(self) -> str: ...

🎨 设计原因：统一骨架使新增 Agent 的成本从"重写整套流程"降低到"实现4个抽象方法"。同时保证了所有 Agent 在记忆召回、置信度校验、归档、事件广播等行为上的一致性，便于后期联调和维护。

CUSTOMER_INTENT_PROMPT = """
判断用户意图，从以下 5 类中选择：
- product_inquiry: 询问具体产品信息（名称/收益率/风险/起投金额）
- policy_explain: 询问政策、法规、监管要求
- faq: 操作流程、常见问题（申购流程、确认时间、手续费）
- chitchat: 问候、感谢、闲聊
- transfer_human: 要求转人工

只返回 JSON: {"intent": "...", "confidence": 0.X}
"""

class CustomerAgent(AgentBase):
    async def classify_intent(self, message: str) -> Intent:
        result = await self.llm.classify(
            system=CUSTOMER_INTENT_PROMPT,
            user=message,
            schema=IntentSchema
        )
        return Intent(**result)

    def _intent_threshold(self) -> float:
        return 0.6  # 低于此值触发"澄清提问"

    def _scenario_name(self) -> str:
        return "知识检索"  # 记忆重排场景

2.3 推理范式

客服 Agent 的推理遵循 "检索优先"（Retrieve-then-Generate） 范式：

python · 推理范式
async def _handle_knowledge_intent(self, intent: str, request: ChatRequest) -> str:
    """知识类意图的推理范式：检索 → 评分 → 生成/兜底"""
    # 1. 检索
    collection = self._select_collection(intent)  # product/policy/faq
    results = await self.rag_tool.search(
        query=request.message,
        collection=collection,
        top_k=5,
        min_score=0.7
    )

    # 2. 评分判断
    if not results or results[0].score < 0.7:
        return self._fallback_response()  # 兜底

    # 3. 构建 System Prompt（含检索结果 + 来源）
    system = self._build_rag_system(results, intent)

    # 4. LLM 生成回答（要求附带来源）
    reply = await self.llm.generate(
        system=system,
        user=request.message,
        temperature=0.3  # 低温度：要求事实准确
    )

    return reply

def _build_rag_system(self, results: list, intent: str) -> str:
    """构建 RAG System Prompt"""
    context = "\n".join(
        f"【来源{i+1}】{r.source}\n{r.content}"
        for i, r in enumerate(results)
    )
    return f"""你是XX科技的智能财富管家。请基于以下知识回答用户问题：

{context}

回答要求：
1. 仅基于上述知识回答，不要编造信息
2. 回答末尾注明引用来源：【来源：《XXX》】
3. 如果知识不足以回答问题，诚实告知并建议联系人工客服
4. 语言友好、专业、简洁"""

2.4 设计原因

  • 为什么用 RAG 而非纯 LLM？——金融产品的收益率、风险等级、起投金额等数据频繁变化，LLM 的训练数据是静态的，无法保证时效性。RAG 从知识库实时检索，确保回答基于最新数据。
  • 为什么 FAQ 用独立集合？——FAQ 数据量小（40条），但命中率极高。独立集合可以用 HNSW 索引实现亚秒级响应，无需与产品/政策数据混用 IVF_FLAT。
  • 为什么 temperature=0.3？——客服回答需要事实准确性，低 temperature 减少 LLM 的自由发挥，防止编造不存在的利率或条款。
  • 为什么 Score 阈值 0.7？——低于 0.7 意味着检索到的知识与用户问题的关联度不足，强行生成容易"幻觉"，此时兜底比编造更安全。

3.3 推理范式

投顾 Agent 的推理遵循 "约束满足 + 图谱推理"（Constraint-Satisfy + Graph-Reason） 范式：

python · 推理范式
async def _handle_recommend(self, request: ChatRequest,
                             profile: CustomerProfile) -> Recommendation:
    """产品推荐推理范式"""
    # Step 1: 硬性约束过滤（适当性匹配）
    candidates = await self.suitability_tool.filter(
        customer_risk_level=profile.risk_level,
        status="在售"
    )
    # 设计原因：先做硬性过滤，避免将不适配的产品送入 LLM 造成误导

    # Step 2: 图谱增强（行业/市场/经理关联分析）
    for product in candidates:
        product.graph_context = await self.graph_tool.query(
            entities=[product.name],
            query_type="product_context",
            max_hops=2
        )
    # 设计原因：图谱提供 RAG 无法覆盖的结构化关联（同行业风险传染）

    # Step 3: 综合排序
    ranked = self.rank_tool.score(
        candidates=candidates,
        weights={
            "return": 0.3,       # 预期收益率
            "risk_match": 0.25,  # 风险匹配度
            "term_match": 0.15,  # 期限匹配度
            "diversify": 0.15,   # 行业分散度
            "graph_signal": 0.15 # 图谱信号强度
        }
    )
    # 设计原因：多因子排序比单一收益率排序更符合投顾专业性

    # Step 4: 推荐理由生成
    top_n = ranked[:3]
    reasons = await self.llm.generate_reasons(
        profile=profile,
        products=top_n,
        template=REASON_TEMPLATE
    )
    # 设计原因：引用画像信息生成个性化理由，而非通用话术

    return Recommendation(products=top_n, reasons=reasons)

REASON_TEMPLATE = """
根据以下客户画像信息，为推荐的产品生成个性化推荐理由：
客户风险等级：{risk_level}
客户资产规模：{total_assets}
客户偏好：{product_preference}

推荐产品：{product_name}（{product_type}，{expected_return}%）
推荐理由需引用画像信息，说明"为什么这个产品适合这位客户"。
"""

3.4 设计原因

  • 为什么先过滤再排序？——适当性匹配是监管红线，不适配的产品根本不应该出现在候选集中。先过滤再排序比先排序后过滤更安全，也避免 LLM 推荐了不适配的产品。
  • 为什么需要图谱增强？——如果客户持仓已集中在新能源行业，推荐时应避免再推荐新能源产品（防止行业集中风险）。这种"持仓穿透"分析只有图谱能在 O(1) 跳数内完成，RAG 做不到。
  • 为什么推荐 3 款而非 10 款？——理财顾问需要的是"精选推荐"而非"产品目录"。3 款足够覆盖不同期限/风险/收益的差异化选择，过多反而增加决策负担。
  • 为什么要生成个性化推荐理由？——通用话术（"该产品收益稳健"）缺乏说服力。引用客户画像（"鉴于您稳健型的风险偏好和债券类偏好..."）能提升理财顾问对 AI 推荐的信任度。

4.3 推理范式

风控 Agent 的推理遵循 "规则匹配 → 交叉验证 → 分级决策"（Rule-Match → Cross-Validate → Grade-Decide） 范式：

python · 推理范式
async def _process_transaction(self, event: TransactionEvent) -> RiskAlert:
    """风控推理范式"""
    # Step 1: 规则匹配（确定性，非 LLM）
    triggered_rules = []
    for rule in self.all_rules:  # 20条规则
        if rule.evaluate(event):
            triggered_rules.append(rule)
    # 设计原因：规则匹配必须是确定性的，不能用 LLM 判断"是否≥5万"

    if not triggered_rules:
        return None  # 正常交易

    # Step 2: 交叉验证（查历史预警 + 行为模式）
    historical_alerts = await self.history_tool.get_alerts(
        customer_id=event.customer_id,
        days=30
    )
    is_repeat = any(
        a.customer_id == event.customer_id and a.alert_type == triggered_rules[0].alert_type
        for a in historical_alerts
    )

    # Step 3: 分级决策
    rule_count = len(triggered_rules)
    if rule_count == 1 and not is_repeat:
        level = "low"     # 轻度预警（蓝色）
    elif rule_count <= 3 or is_repeat:
        level = "medium"  # 中度预警（黄色）
    else:
        level = "high"    # 重度预警（红色）

    # Step 4: 生成预警
    alert = RiskAlert(
        customer_id=event.customer_id,
        alert_type=triggered_rules[0].alert_type,
        alert_level=level,
        trigger_rules=[r.rule_id for r in triggered_rules],
        transaction_ids=[event.transaction_id],
        confidence=self._calc_risk_confidence(triggered_rules, is_repeat),
        trigger_detail=self._format_trigger_detail(triggered_rules, event)
    )

    # Step 5: 持久化 + 广播
    await self.alert_store.save(alert)
    if level == "high":
        await self.event_bus.publish("event:risk_alert", alert.to_dict())
    await self.work_order_tool.create_if_needed(alert)

    return alert

4.4 设计原因

  • 为什么规则匹配不用 LLM？——"交易金额≥5万"是确定性的数值比较，用 LLM 既慢又不保证准确，还引入了不可预测性。规则引擎必须用确定性代码实现。
  • 为什么分级是三级而非两级？——两级（高/低）太粗糙：大量交易和关联交易的严重性完全不同。三级（蓝/黄/红）能更精细地反映风险梯度，且对应不同的处置流程（蓝色→记录、黄色→工单、红色→广播+工单）。
  • 为什么重复触发升级？——同一客户同类型预警反复出现，说明不是一次性异常，而是持续性行为模式。重复触发将置信度从"单次低置信"提升到"持续性高置信"。
  • 为什么重度预警要广播？——红色预警不是风控专员一个人的事，投顾 Agent 需要知道"这个客户有高风险"以调整推荐策略，客服 Agent 需要知道"这个客户来电时需特别注意"。

python · 推理范式
async def _handle_query(self, request: ChatRequest) -> NL2SQLResult:
    """NL2SQL 推理范式"""
    # Step 1: 意图分类 → 选择 Schema + Few-shot
    intent = await self.classify_intent(request.message)
    schema = self._get_schema_for_intent(intent)
    few_shots = self._get_few_shots_for_intent(intent)

    # Step 2: 构建 SQL 生成 Prompt
    system = f"""你是一个SQL专家。根据以下表结构，将自然语言转为SQL。

表结构（DDL）：
{schema}

示例：
{few_shots}

要求：
- 只允许 SELECT 语句
- 使用表别名提高可读性
- 日期用 CURRENT_DATE 而非硬编码"""

    # Step 3: LLM 生成 SQL
    sql = await self.llm.generate(system=system, user=request.message)

    # Step 4: 安全校验（正则）
    DANGEROUS = re.compile(r'\b(DROP|DELETE|UPDATE|INSERT|ALTER|TRUNCATE|GRANT|REVOKE)\b', re.I)
    if DANGEROUS.search(sql):
        return NL2SQLResult(error="不允许执行该操作", sql=None)

    # Step 5: 执行 + 行数限制
    try:
        rows = await self.db.execute(sql + " LIMIT 100")
    except Exception as e:
        return NL2SQLResult(error=f"SQL执行失败: {e}", sql=sql)

    # Step 6: 结果解读
    interpretation = await self.llm.interpret(
        query=request.message,
        sql=sql,
        result_preview=rows[:10],  # 只给前10行给LLM，省Token
        total_rows=len(rows)
    )

    # Step 7: 缓存
    cache_key = hashlib.md5(f"{request.message}:{schema}".encode()).hexdigest()
    await self.cache.set(f"nl2sql:{cache_key}", json.dumps({
        "sql": sql, "rows": rows, "interpretation": interpretation
    }), ttl=600)  # 10分钟

    return NL2SQLResult(sql=sql, rows=rows, interpretation=interpretation)

4.4 设计原因

  • 为什么用动态 Schema 筛选？——10 张表的 DDL 全部注入会超过 4000 token，既浪费又降低生成质量。按意图筛选到 1-3 张表，LLM 聚焦度更高。
  • 为什么只给前 10 行给 LLM 解读？——LLM 不擅长处理 100 行数据。给 10 行样例 + 总数统计，LLM 就能生成准确的文字描述，同时节省 90% 的 Token。
  • 为什么缓存 10 分钟？——金融数据查询有实时性要求，但同一问题在 10 分钟内重复问的概率很高（比如开会时多个人问同一问题）。10 分钟平衡了实时性和性能。
  • 为什么用正则而非 AST 校验？——正则简单直接，覆盖所有危险操作。AST 校验更精确但实现复杂。对于内部系统，正则的误判率可接受（宁可多拦截一条也不能放过一条）。

class BusinessOperatorAgent(AgentBase):
    async def _handle_operation(self, request: ChatRequest) -> OperationResult:
        """业务操作推理范式"""
        # Step 1: 意图识别 + 参数提取（Function Calling）
        intent, params = await self._parse_operation(request.message)

        # Step 2: 参数完整性校验
        required = self._get_required_params(intent)
        missing = [p for p in required if p not in params]
        if missing:
            return self._ask_missing_params(missing)

        # Step 3: RBAC 权限校验
        if not self._check_permission(request.user_role, intent):
            return OperationResult(
                status="denied",
                reply=f"您（{request.user_role}）无权执行{intent}操作"
            )

        # Step 4: 二次确认（高风险操作）
        if self._needs_confirmation(intent, params):
            confirm_msg = self._build_confirm_message(intent, params)
            if not await self._wait_for_confirm(confirm_msg):
                return OperationResult(status="cancelled")

        # Step 5: 执行 API
        try:
            result = await self._execute_api(intent, params)
        except BusinessException as e:
            return OperationResult(status="failed", reply=str(e))

        # Step 6: 执行验证 + 工单
        if result.success:
            await self.work_order_tool.create_operation_order(
                intent=intent, params=params, result=result
            )
            # 大额交易通知风控
            if self._is_large_transaction(intent, params):
                await self.event_bus.publish("event:large_transaction", {
                    "customer_id": params["customer_id"],
                    "amount": params.get("amount", 0),
                    "operation": intent
                })

        return OperationResult(
            status="success" if result.success else "failed",
            reply=result.format_human_message()
        )

6.4 设计原因

  • 为什么用 Function Calling 而非 Prompt 提取？——Function Calling 有结构化输出保证（JSON Schema），参数类型和必填项有 LLM 内置校验。正则提取无法处理"帮我给客户张三买10万XX稳健增利"这种需要同时提取客户名、金额、产品名的复杂指令。
  • 为什么二次确认阈值是 1 万/5 万？——申购 1 万是中等金额，对大多数客户而言需要确认；转账 5 万是反洗钱监管的关注线。阈值可配置，但默认值需要覆盖大多数正常交易场景。
  • 为什么执行后要生成工单？——工单是审计留痕的载体。没有工单的操作是"不可追溯"的，不符合金融合规要求。工单包含操作人、操作时间、操作内容、执行结果，是事后审计的关键数据。
  • 为什么大额交易要通知风控？——业务操作和风控监测不是孤立的。一笔申购操作本身是正常的，但如果该客户今天已经被风控标记为"高频交易"，则这次操作可能进一步触发预警。跨 Agent 的信息联动是风控体系的核心价值。

7.3 协作场景示例

场景一：客户咨询 → 申购 → 风控联动

  2. 客服 Agent通过 RAG 检索产品知识库，推荐 3 款产品
  3. 客户决定申购，客服 Agent 引导到业务操作 Agent（或提示客户联系理财顾问）
  4. 理财顾问通过业务操作 Agent 执行申购："帮客户A申购10万XX稳健增利债券A"
  5. 业务操作 Agent校验权限 → 二次确认 → 执行申购
  6. 业务操作 Agent发布 event:large_transaction（金额10万 > 5万阈值）
  7. 风控 Agent接收事件 → 匹配规则 R001（单笔≥5万）→ 轻度预警（蓝色）
  8. 风控 Agent查历史：该客户30天内无预警 → 保持蓝色，仅记录

场景二：风控 → 投顾联动

  1. 风控 Agent监测到客户B连续3天大额申购 → 触发 R001+R002+R003 → 红色预警
  2. 风控 Agent发布 event:risk_alert（alert_level=high）
  3. 投顾 Agent接收事件 → 在客户B画像中标记 "高风险-待核实"
  4. 投顾 Agent下次为客户B做推荐时，自动降低高风险产品的推荐权重
  5. 客服 Agent接收事件 → 客户B来电时，客服界面显示"该客户存在风控预警"

8.2 工具调用协议

所有工具遵循统一的调用协议，确保 Agent 可以跨工具协作：

json · 工具请求
{
    "tool_name": "rag_search",
    "parameters": {
        "query": "有什么年化5%以上的稳健型理财？",
        "collection": "fin_product_collection",
        "top_k": 5,
        "min_score": 0.7
    },
    "caller_agent": "customer",
    "trace_id": "uuid-for-tracing"
}
json · 工具响应
{
    "tool_name": "rag_search",
    "result": [
        {
            "content": "XX稳健增利债券A，预期年化5.2%...",
            "score": 0.89,
            "source": "个人理财产品手册.md"
        }
    ],
    "execution_time_ms": 150,
    "status": "success"
}

💡 执行时间追踪：每个工具响应都携带 execution_time_ms，用于性能监控和超时降级。当某个工具执行超过阈值时（如 Milvus > 2s），骨架自动触发降级策略，不会让整个 Agent 请求挂起。
